> Running example used in many answers: a **Student Management / E-commerce API**.

# 🟢 LEVEL 1: BASIC

## 1. C# Fundamentals

### 1. What is C# and where is it used?
C# (say "C sharp") is a modern, object-oriented, type-safe language made by Microsoft. It's used for web APIs (ASP.NET Core), desktop apps (WPF/WinForms), mobile apps (MAUI), games (Unity), cloud services (Azure), and microservices.

### 2. What is .NET?
.NET is a free, open-source platform for building apps. It gives you: a runtime (runs your code), a huge class library (collections, file I/O, HTTP), and tools (`dotnet` CLI). C#, F#, and VB can all run on it.

### 3. .NET Framework vs .NET Core vs modern .NET?
| | .NET Framework | .NET Core | Modern .NET (5, 6, 7, 8, 9...) |
|---|---|---|---|
| OS | Windows only | Cross-platform | Cross-platform |
| Status | Legacy (4.8 last) | Replaced | Current, unified |
| Open source | Partly | Yes | Yes |
| Performance | Good | Better | Best |

Since .NET 5 the word "Core" was dropped. For new projects always choose modern .NET (LTS versions such as 8).

### 4. What is CLR?
**Common Language Runtime**: the engine that runs your compiled code. It does JIT compilation, garbage collection, exception handling, type safety, and security.

### 5. What is CTS?
**Common Type System**: defines how types (int, class, struct, interface) are declared and used so that all .NET languages understand each other. Example: C# `int` = VB `Integer` = `System.Int32`.

### 6. What is CLS?
**Common Language Specification**: a small set of rules every language must follow so its code can be used by other .NET languages. (e.g., don't expose public members that differ only by case.)

### 7. Managed vs unmanaged code?
- **Managed**: runs under the CLR, which handles memory (GC) and safety. Example: normal C#.
- **Unmanaged**: runs directly on the OS and you manage memory yourself. Example: C/C++ DLLs.

### 8. Value types vs reference types?
- **Value types** (`int`, `bool`, `struct`, `enum`) store the value directly (usually on the stack). Copying makes an independent copy.
- **Reference types** (`class`, `string`, arrays, `interface`) store an address pointing to an object on the heap. Copying copies the address, so both variables point to the same object.

```csharp
int a = 5; int b = a; b = 10;          // a is still 5

class Student { public string Name; }
var s1 = new Student { Name = "Ali" };
var s2 = s1; s2.Name = "Omar";         // s1.Name is also "Omar"
```

### 9. Boxing and unboxing?
- **Boxing**: converting a value type into `object` (copied to the heap). 
- **Unboxing**: converting it back. Both cost performance.

```csharp
int x = 10;
object o = x;       // boxing
int y = (int)o;     // unboxing
```
Avoid it by using generics (`List<int>` instead of `ArrayList`).

### 10. What is a class?
A blueprint that defines data (fields/properties) and behavior (methods).
```csharp
public class Student { public int Id { get; set; } public string Name { get; set; } }
```

### 11. What is an object?
A real instance of a class created with `new`. `var s = new Student();`

### 12. What is a constructor?
A special method with the class name that runs when an object is created. It sets the initial state.
```csharp
public class Student {
    public string Name { get; }
    public Student(string name) => Name = name;
}
```

### 13. What is a static class?
A class that can't be instantiated and contains only static members. Used for helpers.
```csharp
public static class MathHelper { public static int Square(int n) => n * n; }
```

### 14. const vs readonly vs static readonly?
- `const`: compile-time constant, must be assigned at declaration, implicitly static. Only primitives/strings.
- `readonly`: assigned at declaration or in the constructor; value can differ per instance.
- `static readonly`: one value shared by all instances, assigned at runtime (once).

```csharp
public const double Pi = 3.14;
public readonly Guid Id = Guid.NewGuid();
public static readonly DateTime StartedAt = DateTime.UtcNow;
```

### 15. Access modifiers?
Keywords controlling visibility: `public`, `private`, `protected`, `internal`, `protected internal`, `private protected`, `file`.

### 16. public vs private vs protected vs internal?
- `public`: everywhere.
- `private`: only inside the same class (default for members).
- `protected`: the class and its derived classes.
- `internal`: anywhere in the same assembly (project).

### 17. Inheritance?
A class reuses another class's members using `:`.
```csharp
public class Person { public string Name { get; set; } }
public class Student : Person { public int RollNo { get; set; } }
```

### 18. Polymorphism?
"Many forms": the same call behaves differently by object type.
```csharp
public abstract class Payment { public abstract void Pay(); }
public class CardPayment : Payment { public override void Pay() => Console.WriteLine("Card"); }
public class UpiPayment  : Payment { public override void Pay() => Console.WriteLine("UPI"); }
Payment p = new UpiPayment(); p.Pay();   // UPI
```

### 19. Encapsulation?
Hide internal data and expose it safely through methods/properties.
```csharp
public class BankAccount {
    private decimal _balance;
    public void Deposit(decimal amt) { if (amt <= 0) throw new ArgumentException(); _balance += amt; }
    public decimal Balance => _balance;
}
```

### 20. Abstraction?
Show *what* an object does and hide *how*. You press "Pay" without knowing the gateway's internal code. Done via abstract classes and interfaces.

### 21. What is an interface?
A contract of members with no implementation (default methods allowed in newer C#). A class that implements it must provide all members.
```csharp
public interface IEmailSender { Task SendAsync(string to, string body); }
```

### 22. Abstract class?
A class that can't be instantiated and may have both implemented and abstract members. It's a partial base for related classes.

### 23. Interface vs abstract class?
| Interface | Abstract class |
|---|---|
| Contract only (can have default methods) | Can have fields, constructors, code |
| A class can implement many | A class can inherit only one |
| "Can do" (ICanFly) | "Is a" (Animal) |

### 24. Overloading vs overriding?
- **Overloading** (compile-time): same method name, different parameters, same class.
- **Overriding** (run-time): a child class replaces a `virtual`/`abstract` parent method.

### 25. `virtual` keyword?
Marks a base method that derived classes *may* override.

### 26. `override` keyword?
Used in a derived class to replace a virtual/abstract base method.
```csharp
class Animal { public virtual string Speak() => "..."; }
class Dog : Animal { public override string Speak() => "Woof"; }
```

### 27. `sealed`?
On a class: it can't be inherited. On an overridden method: it can't be overridden further. Used for security/performance.

### 28. Partial class?
A class split across several files, merged at compile time. Common with generated code (EF scaffolding, designers).

### 29. Properties?
Members that look like fields but use `get`/`set` accessors, allowing validation.
```csharp
private int _age;
public int Age { get => _age; set { if (value < 0) throw new Exception(); _age = value; } }
```

### 30. Auto-implemented property?
Compiler creates the hidden field: `public string Name { get; set; }`. Variants: `{ get; init; }`, `{ get; private set; }`.

### 31. Nullable type?
Lets a value type hold `null`: `int? age = null;` (`Nullable<int>`). Check with `age.HasValue` or `age ?? 0`.

### 32. var vs dynamic vs object?
- `var`: type decided at **compile time**, still strongly typed.
- `dynamic`: type resolved at **run time**; no compile checks (errors appear at runtime).
- `object`: base of all types; needs casting to use specific members.

```csharp
var a = 10;           // int
dynamic d = 10; d = "hi";   // allowed
object o = 10; int n = (int)o;
```

### 33. Enums?
Named integer constants.
```csharp
public enum OrderStatus { Pending = 1, Paid, Shipped, Cancelled }
```

### 34. Structs?
Value-type containers for small data (e.g., `Point`, `DateTime`).
```csharp
public struct Point { public int X, Y; }
```

### 35. Class vs struct?
Class: reference type, heap, supports inheritance, can be null. Struct: value type, usually stack, no inheritance, copied on assignment. Use struct for small (<16 bytes), immutable data.

### 36. Record?
A type built for immutable data with value-based equality, `with` copy and auto `ToString`.
```csharp
public record StudentDto(int Id, string Name);
var a = new StudentDto(1, "Ali");
var b = a with { Name = "Omar" };
Console.WriteLine(a == new StudentDto(1, "Ali")); // True
```

### 37. Pattern matching?
Checking a value's shape/type in `is` and `switch`.
```csharp
string Describe(object o) => o switch {
    int n when n > 100 => "big number",
    int            => "number",
    string { Length: 0 } => "empty text",
    null           => "null",
    _              => "other"
};
```

### 38. Nullable reference types?
A compile-time feature (`<Nullable>enable</Nullable>`) that warns when you might dereference null. `string` = never null, `string?` = may be null.

### 39. String immutability?
A string can't be changed after creation; every "change" makes a new string. Benefits: thread-safe, hashable, safe to share.

### 40. String vs StringBuilder?
Use `StringBuilder` when you concatenate many times in a loop; it modifies a buffer instead of creating new strings.
```csharp
var sb = new StringBuilder();
for (int i = 0; i < 1000; i++) sb.Append(i).Append(',');
string result = sb.ToString();
```

## 2. Collections & LINQ

### 41. Array?
A fixed-size, indexed collection of one type: `int[] nums = new int[5];`

### 42. Array vs List<T>?
Array: fixed size, slightly faster. `List<T>`: dynamic size (Add/Remove), more convenient. Use List in most business code.

### 43. Dictionary<TKey,TValue>?
Key/value collection with near O(1) lookup.
```csharp
var stock = new Dictionary<string,int> { ["Pen"] = 10 };
if (stock.TryGetValue("Pen", out var qty)) Console.WriteLine(qty);
```

### 44. IEnumerable vs ICollection vs IList?
- `IEnumerable<T>`: only iterate (foreach).
- `ICollection<T>`: + Count, Add, Remove.
- `IList<T>`: + index access (`list[0]`), Insert.
Return the narrowest type your caller needs.

### 45. IEnumerable<T> vs IQueryable<T>?
- `IEnumerable`: in-memory, LINQ runs in your app (LINQ to Objects).
- `IQueryable`: builds an expression tree translated to SQL by EF Core, so filtering happens in the database.
```csharp
var q = db.Students.Where(s => s.Age > 18);  // IQueryable: WHERE in SQL
var list = q.ToList();                       // query executes now
```
If you convert to IEnumerable too early (`.AsEnumerable()`), the whole table loads into memory.

### 46. LINQ?
Language Integrated Query: one syntax to query lists, databases, XML.
`var adults = students.Where(s => s.Age >= 18).ToList();`

### 47. Why is LINQ useful?
Short, readable, type-safe, works with many data sources, composable.

### 48. Deferred execution?
A query doesn't run when you write it, only when you enumerate it (foreach, ToList, Count...).
```csharp
var q = nums.Where(n => n > 2);
nums.Add(10);               // added before enumeration
foreach (var n in q) { }    // includes 10
```

### 49. Immediate execution?
Operators like `ToList()`, `ToArray()`, `Count()`, `First()`, `Sum()` run the query immediately and return a result.

### 50. Where() vs Select()?
`Where` **filters** rows. `Select` **transforms/projects** each item.
```csharp
students.Where(s => s.Age > 18).Select(s => s.Name);
```

### 51. First() vs FirstOrDefault()?
`First()` throws `InvalidOperationException` if nothing matches. `FirstOrDefault()` returns `null`/default.

### 52. Single() vs SingleOrDefault()?
`Single()` expects **exactly one** match (throws on 0 or 2+). `SingleOrDefault()` allows 0 (returns default) but throws on 2+. Use for unique lookups (e.g., by email).

### 53. Any() vs Count()?
`Any()` stops at the first match (fast). `Count()` counts everything. To check existence use `Any()`, not `Count() > 0`.

### 54. OrderBy vs OrderByDescending?
Ascending vs descending sort. Chain with `ThenBy`: `.OrderBy(s => s.City).ThenByDescending(s => s.Marks)`.

### 55. GroupBy()?
Groups items by key.
```csharp
var byCity = students.GroupBy(s => s.City)
                     .Select(g => new { City = g.Key, Total = g.Count() });
```

### 56. Join() in LINQ?
Like SQL inner join.
```csharp
var result = orders.Join(customers, o => o.CustomerId, c => c.Id,
                         (o, c) => new { c.Name, o.Total });
```

### 57. SelectMany()?
Flattens a list of lists into one list.
```csharp
var allItems = orders.SelectMany(o => o.Items);
```

### 58. What does ToList() do internally?
It enumerates the source immediately, copies each item into a new `List<T>` (allocates memory) and ends deferred execution. With EF it sends the SQL query.

### 59. What if you enumerate an IEnumerable multiple times?
The query re-runs every time (and a DB query hits the DB again). Fix: materialize once with `ToList()`.

### 60. LINQ-to-Objects vs LINQ-to-Entities?
Objects: runs in memory with delegates (`Func`). Entities: translated into SQL with expression trees (`Expression<Func>`); some C# methods can't be translated.

## 🟢 3. Exception Handling

### 61. What is an exception?
A run-time error object that interrupts normal flow (e.g., `DivideByZeroException`, `NullReferenceException`).

### 62. How does try-catch-finally work?
`try` = risky code, `catch` = handle error, `finally` = always runs (cleanup).
```csharp
try { var data = File.ReadAllText("a.txt"); }
catch (FileNotFoundException ex) { logger.LogError(ex, "Missing file"); }
finally { Console.WriteLine("Done"); }
```

### 63. throw vs throw ex?
`throw;` keeps the original stack trace. `throw ex;` resets it (you lose where it really failed). Always use `throw;` to rethrow.

### 64. Multiple catch blocks?
Yes. Order from most specific to most general. Use `when` filters: `catch (HttpRequestException ex) when (ex.StatusCode == 404)`.

### 65. Custom exception?
Your own exception type for domain errors.
```csharp
public class InsufficientBalanceException : Exception {
    public InsufficientBalanceException(decimal bal) : base($"Balance {bal} too low") { }
}
```

### 66. Should exceptions be used for normal business logic?
No. They're slow and hide the flow. Use return values/`Result` objects/`TryParse` for expected cases (e.g., "user not found"). Use exceptions for truly exceptional failures.

### 67. What if an exception isn't handled?
It bubbles up the call stack. In ASP.NET Core without handling you get a 500 error (stack trace in Development); in a console app the process crashes.

### 68. Global exception handling?
One central place that catches all unhandled exceptions and returns a consistent response, so you don't write try/catch in every controller.

### 69. How to implement it in ASP.NET Core?
Modern way: `IExceptionHandler` (NET 8+).
```csharp
public class GlobalExceptionHandler : IExceptionHandler {
    public async ValueTask<bool> TryHandleAsync(HttpContext ctx, Exception ex, CancellationToken ct) {
        var problem = new ProblemDetails {
            Status = ex is KeyNotFoundException ? 404 : 500,
            Title = "An error occurred", Detail = ex.Message };
        ctx.Response.StatusCode = problem.Status.Value;
        await ctx.Response.WriteAsJsonAsync(problem, ct);
        return true;
    }
}
// Program.cs
builder.Services.AddExceptionHandler<GlobalExceptionHandler>();
builder.Services.AddProblemDetails();
app.UseExceptionHandler();
```
(Older way: custom middleware with try/catch around `next()`.)

### 70. ProblemDetails?
A standard JSON error format (RFC 7807/9457): `type`, `title`, `status`, `detail`, `instance`.
```json
{ "type":"https://tools.ietf.org/html/rfc9110#section-15.5.5",
  "title":"Not Found","status":404,"detail":"Student 12 not found" }
```

## 🟢 4. ASP.NET Core Fundamentals

### 71. What is ASP.NET Core?
A free, cross-platform, high-performance framework for building web apps, REST APIs, real-time apps (SignalR), and gRPC services on .NET.

### 72. Why use it for backend development?
Fast (one of the top frameworks in benchmarks), cross-platform, built-in DI, config, logging, strong security, great tooling, Docker/cloud friendly, long-term support.

### 73. What is middleware?
A small component in the request pipeline. Each one can handle the request, pass it to the next, and act on the response (logging, auth, CORS, errors).

### 74. How does the request pipeline work?
Request → Middleware 1 → Middleware 2 → ... → Endpoint → response travels back through the same middleware in reverse order.
```
Request → [ExceptionHandler] → [HTTPS] → [Auth] → [Endpoint]
Response ← [ExceptionHandler] ← [HTTPS] ← [Auth] ← [Endpoint]
```

### 75. What is Program.cs?
The app's entry point. It (1) creates the builder, (2) registers services (DI), (3) builds the app, (4) configures the middleware pipeline, (5) runs.
```csharp
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddControllers();
var app = builder.Build();
app.UseHttpsRedirection();
app.UseAuthorization();
app.MapControllers();
app.Run();
```

### 76. What is dependency injection?
Instead of a class creating its own dependencies with `new`, they are *given* (injected) to it, usually in the constructor, by a container.
```csharp
public class OrderService {
    private readonly IEmailSender _email;
    public OrderService(IEmailSender email) => _email = email;   // injected
}
```

### 77. Why is it important?
Loose coupling, easy unit testing (swap with fakes), centralized lifetime management, easy to change implementations.

### 78. Three DI lifetimes?
Singleton, Scoped, Transient.

### 79. Singleton?
One instance for the whole app lifetime. Good for caches, config, stateless helpers. Must be thread-safe.
`services.AddSingleton<ICacheService, CacheService>();`

### 80. Scoped?
One instance per HTTP request. Default for `DbContext`, services using it.
`services.AddScoped<IStudentService, StudentService>();`

### 81. Transient?
A new instance every time it is requested. For lightweight, stateless services.
`services.AddTransient<IValidator, MyValidator>();`

### 82. Singleton vs Scoped vs Transient?
| Lifetime | Created | Example |
|---|---|---|
| Singleton | once per app | in-memory cache |
| Scoped | once per request | DbContext, UnitOfWork |
| Transient | each injection | small helper/mapper |

### 83. Configuration in ASP.NET Core?
A layered key/value system that reads from JSON files, environment variables, command-line args, user secrets, Azure Key Vault. Later sources override earlier ones.

### 84. appsettings.json?
The main config file (connection strings, logging levels, feature settings). Don't put secrets here.

### 85. appsettings.Development.json?
Overrides values for the Development environment (`ASPNETCORE_ENVIRONMENT=Development`), e.g., verbose logging, local DB. Similarly `.Production.json`.

### 86. IConfiguration?
Interface to read config.
```csharp
var conn = builder.Configuration.GetConnectionString("Default");
var key  = configuration["Jwt:Key"];
```

### 87. Options pattern?
Bind a config section to a strongly-typed class and inject it.
```csharp
public class JwtOptions { public string Issuer { get; set; } public string Key { get; set; } }
builder.Services.Configure<JwtOptions>(builder.Configuration.GetSection("Jwt"));

public class TokenService(IOptions<JwtOptions> opt) { private readonly JwtOptions _o = opt.Value; }
```
`IOptionsSnapshot` (reloads per request), `IOptionsMonitor` (live change notifications).

### 88. Environment variables?
OS-level key/values. Used to set environment and secrets in containers/servers. Nested keys use double underscore: `ConnectionStrings__Default`.

### 89. How to store connection strings?
- Dev: `dotnet user-secrets` or appsettings.Development.json.
- Prod: environment variables or a secret manager (Azure Key Vault, AWS Secrets Manager). Never commit them to Git.

### 90. Kestrel?
The default cross-platform web server in ASP.NET Core. In production it often sits behind a reverse proxy (Nginx, IIS, YARP) for TLS, load balancing, etc.

## 🟢 5. REST API Fundamentals

### 91. What is an API?
Application Programming Interface: a way for programs to talk. A mobile app calls your API to get student data.

### 92. What is REST?
Representational State Transfer: an architectural style that uses HTTP to work with **resources** identified by URLs.

### 93. RESTful API?
An API that follows REST principles: resources as nouns, HTTP verbs for actions, stateless, standard status codes.
`GET /api/students/5`, `POST /api/students`, `DELETE /api/students/5`.

### 94. REST principles?
Client-server, stateless, cacheable, uniform interface, layered system, (optional) code on demand.

### 95. What is a resource?
Any "thing" the API exposes: student, order, product. It has an identifier (URL) and a representation (JSON).

### 96. Endpoint?
A specific URL + HTTP method, e.g., `GET /api/orders/10`.

### 97. HTTP?
HyperText Transfer Protocol: request/response protocol of the web. A request has method, URL, headers, body. The response has status code, headers, body.

### 98. HTTP methods?
GET, POST, PUT, PATCH, DELETE (plus HEAD, OPTIONS).

### 99. GET?
Read data. Safe and idempotent, no body normally. `GET /students?page=1`.

### 100. POST?
Create a new resource (or run an action). Not idempotent. Returns `201 Created` + `Location` header.

### 101. PUT?
**Replace** the whole resource (send all fields). Idempotent.

### 102. PATCH?
**Partially update** a resource (send only changed fields).

### 103. DELETE?
Remove a resource. Idempotent. Returns 204 (or 200 with body).

### 104. GET vs POST?
GET: reads, parameters in URL, cacheable, safe. POST: sends data in the body, creates/changes data, not cached, not idempotent.

### 105. PUT vs PATCH?
PUT replaces everything (missing fields become null/default). PATCH changes only the fields sent.

### 106. PUT vs POST?
POST: server decides the ID (`POST /students`). PUT: client targets a known URL (`PUT /students/5`) and repeating it gives the same result.

### 107. HTTP status code?
A 3-digit number summarizing the result: 1xx info, 2xx success, 3xx redirect, 4xx client error, 5xx server error.

### 108. 200 OK?
Request succeeded; response has the data.

### 109. 201 Created?
A new resource was created. Include `Location: /api/students/12`.

### 110. 204 No Content?
Success, nothing to return (typical for PUT/DELETE).

### 111. 400 Bad Request?
Client sent invalid data (bad JSON, failed validation).

### 112. 401 Unauthorized?
Not authenticated: missing/invalid/expired token. ("Who are you?")

### 113. 403 Forbidden?
Authenticated but not allowed. ("I know you, but you can't do this.")

### 114. 404 Not Found?
Resource doesn't exist.

### 115. 409 Conflict?
Request conflicts with current state (duplicate email, concurrency conflict).

### 116. 500 Internal Server Error?
Unexpected server failure (bug, DB down). Never leak stack traces in production.

### 117. Idempotency?
Calling the operation many times has the same effect as calling once. `DELETE /students/5` twice → student is gone either way.

### 118. Which methods are idempotent?
GET, PUT, DELETE, HEAD, OPTIONS. POST and (generally) PATCH are not.

### 119. Statelessness?
The server stores no client session between requests. Each request carries everything needed (token, parameters). This makes horizontal scaling easy.

### 120. Content negotiation?
Client says what format it wants via `Accept: application/json` (or xml); server replies with a matching `Content-Type`. If unsupported → 406.

## 🟢 6. ASP.NET Core Web API

### 121. Controller?
A class that groups endpoints (actions) handling HTTP requests.
```csharp
[ApiController]
[Route("api/[controller]")]
public class StudentsController : ControllerBase { }
```

### 122. ControllerBase?
Base class with API features (`Ok()`, `NotFound()`, `CreatedAtAction()`) but no View support.

### 123. Controller vs ControllerBase?
`Controller` = ControllerBase + MVC view support (`View()`). For APIs use `ControllerBase`.

### 124. [ApiController]?
Enables API conveniences: automatic 400 on invalid ModelState, automatic binding inference (`[FromBody]` for complex types), ProblemDetails responses, attribute routing required.

### 125. Routing?
Mapping an incoming URL + method to an action method.

### 126. Attribute vs conventional routing?
Attribute: routes defined on controllers/actions (`[HttpGet("{id}")]`), best for APIs. Conventional: a global pattern like `{controller}/{action}/{id?}`, used in MVC web apps.

### 127. [Route]?
Defines the URL template: `[Route("api/students")]` or `api/[controller]`.

### 128. [HttpGet]?
Action responds to GET. `[HttpGet("{id:int}")]`

### 129. [HttpPost]?
Action responds to POST (create).

### 130. [HttpPut]?
Responds to PUT (replace).

### 131. [HttpPatch]?
Responds to PATCH (partial update).

### 132. [HttpDelete]?
Responds to DELETE.

### 133. Route parameter?
A value inside the path: `/students/5` → `{id}`.

### 134. Query parameter?
A value after `?`: `/students?city=Pune&page=2`.

### 135. Route vs query parameter?
Route: identifies a specific resource (required). Query: optional filters, sorting, paging.

### 136. [FromBody]?
Bind from the JSON request body. `Create([FromBody] CreateStudentDto dto)`

### 137. [FromRoute]?
Bind from the URL path: `Get([FromRoute] int id)`

### 138. [FromQuery]?
Bind from the query string: `Search([FromQuery] string name)`

### 139. [FromHeader]?
Bind from an HTTP header: `Get([FromHeader(Name="X-Correlation-Id")] string id)`

### 140. Model binding?
Automatically converting request data (route, query, body, headers, form) into C# parameters/objects.

### 141. Model validation?
Checking bound data against rules (required, range, length) before running business code.

### 142. ModelState?
Holds binding/validation results. `ModelState.IsValid`; with `[ApiController]` an invalid state auto-returns 400.

### 143. ActionResult<T>?
Return type that can be either a `T` value or any HTTP result.
```csharp
public async Task<ActionResult<StudentDto>> Get(int id) {
    var s = await _service.GetAsync(id);
    return s is null ? NotFound() : Ok(s);
}
```

### 144. IActionResult vs ActionResult<T>?
`IActionResult` doesn't state the success type (weak Swagger docs). `ActionResult<T>` shows the type `T` for Swagger and allows `return dto;` directly.

### 145. Returning different status codes?
```csharp
return Ok(data);                 // 200
return CreatedAtAction(nameof(Get), new { id }, dto); // 201
return NoContent();              // 204
return BadRequest("msg");        // 400
return NotFound();               // 404
return StatusCode(503);          // custom
return Conflict();               // 409
```

### 146. Returning JSON?
Controllers return objects; the JSON formatter serializes automatically: `return Ok(student);`. Minimal API: `Results.Ok(student)`.

### 147. JSON serialization?
Converting C# objects to JSON text (and back = deserialization).

### 148. System.Text.Json?
Built-in, fast JSON library of .NET (default in ASP.NET Core).
```csharp
var json = JsonSerializer.Serialize(student);
var obj  = JsonSerializer.Deserialize<Student>(json);
```
Configure with `AddJsonOptions(o => o.JsonSerializerOptions.PropertyNamingPolicy = JsonNamingPolicy.CamelCase)`.

### 149. DTO?
Data Transfer Object: a simple class/record that defines the shape of data sent/received by the API.
```csharp
public record StudentDto(int Id, string Name, string Email);
```

### 150. Why DTOs instead of entities?
Security (don't leak `PasswordHash`), stability (DB changes don't break clients), avoid over-posting, avoid circular references, shape data for the client, smaller payloads.

# 🟡 LEVEL 2: INTERMEDIATE

## 7. Entity Framework Core

### 151. What is EF Core?
A lightweight ORM from Microsoft. You work with C# classes and LINQ; EF generates SQL.

### 152. EF Core vs ADO.NET?
ADO.NET: manual SQL, readers, fastest, lots of boilerplate. EF Core: productivity, migrations, change tracking, a bit more overhead. Many teams use EF Core for CRUD and Dapper/ADO.NET for hot paths.

### 153. ORM?
Object-Relational Mapper: maps tables ↔ classes, rows ↔ objects.

### 154. DbContext?
The session with the database: holds DbSets, tracks changes, saves changes.
```csharp
public class AppDbContext : DbContext {
    public AppDbContext(DbContextOptions<AppDbContext> o) : base(o) { }
    public DbSet<Student> Students => Set<Student>();
}
// Program.cs
builder.Services.AddDbContext<AppDbContext>(o => o.UseSqlServer(conn));
```

### 155. DbSet<T>?
Represents a table/collection of entity `T` you can query and modify.

### 156. Entity?
A class mapped to a table. `Student` → `Students` table.

### 157. Primary key?
Column(s) that uniquely identify a row. By convention a property named `Id` or `StudentId`.

### 158. Foreign key?
A column referencing another table's primary key (`Order.CustomerId`).

### 159. Navigation property?
A property that links related entities: `Order.Customer`, `Customer.Orders`.

### 160. Migration?
A versioned C# file describing schema changes, so DB structure evolves with code.

### 161. Create a migration?
`dotnet ef migrations add AddStudentTable`

### 162. Apply a migration?
`dotnet ef database update` (or generate a script: `dotnet ef migrations script`, preferred in production; or a migration bundle).

### 163. What happens on SaveChangesAsync()?
EF runs `DetectChanges`, builds INSERT/UPDATE/DELETE commands for tracked entities, executes them in **one transaction**, then updates generated values (identity, rowversion) and resets tracking state.

### 164. Change tracking?
EF remembers original values of loaded entities and compares them to detect what to save.

### 165. AsNoTracking()?
Tells EF not to track returned entities, so queries are faster and use less memory.

### 166. When to use it?
For read-only queries (GET endpoints, reports, lists).
`await db.Students.AsNoTracking().ToListAsync();`

### 167. Eager loading?
Load related data in the same query with `Include`.
`db.Orders.Include(o => o.Items)`

### 168. Lazy loading?
Related data loads on first access (needs proxies + virtual navigation). Easy but risks N+1; usually avoided in APIs.

### 169. Explicit loading?
Load related data manually later.
`await db.Entry(order).Collection(o => o.Items).LoadAsync();`

### 170. Include() vs ThenInclude()?
`Include` loads the first level; `ThenInclude` goes deeper.
```csharp
db.Orders.Include(o => o.Items).ThenInclude(i => i.Product);
```

### 171. Shadow property?
A column in the DB with no property in the class. `builder.Property<DateTime>("LastUpdated");` Access through `db.Entry(e).Property("LastUpdated")`.

### 172. Fluent API?
Configuring the model in code inside `OnModelCreating` (more powerful than attributes).
```csharp
modelBuilder.Entity<Student>().Property(s => s.Name).HasMaxLength(100).IsRequired();
```

### 173. Data annotations vs Fluent API?
Annotations: attributes on the class, simple (`[Required]`, `[MaxLength]`). Fluent: all features, keeps entities clean, wins on conflict. Many teams use fluent only.

### 174. Entity configuration?
Grouping mapping rules per entity using `IEntityTypeConfiguration<T>` and `ApplyConfigurationsFromAssembly`.
```csharp
public class StudentConfig : IEntityTypeConfiguration<Student> {
    public void Configure(EntityTypeBuilder<Student> b) {
        b.HasKey(x => x.Id);
        b.HasIndex(x => x.Email).IsUnique();
    }
}
```

### 175. Composite key?
Primary key made of multiple columns: `b.HasKey(e => new { e.StudentId, e.CourseId });` (enrollment table).

### 176. Optimistic concurrency?
Assume conflicts are rare; detect them at save time with a version column. If someone else changed the row, EF throws `DbUpdateConcurrencyException`.
```csharp
public byte[] RowVersion { get; set; }
b.Property(x => x.RowVersion).IsRowVersion();
```

### 177. Transaction?
A group of operations that all succeed or all fail.

### 178. Transaction in EF Core?
`SaveChanges` is already transactional. For multiple saves:
```csharp
await using var tx = await db.Database.BeginTransactionAsync();
try {
    db.Orders.Add(order); await db.SaveChangesAsync();
    stock.Qty -= 1;       await db.SaveChangesAsync();
    await tx.CommitAsync();
} catch { await tx.RollbackAsync(); throw; }
```

### 179. N+1 problem?
1 query to load N parents + N extra queries to load each parent's children.
```csharp
var orders = db.Orders.ToList();            // 1 query
foreach (var o in orders) Console.WriteLine(o.Items.Count); // N queries (lazy)
```

### 180. Preventing N+1?
Use `Include`, projection (`Select`), split queries, or batch load related data with one `WHERE IN` query. Watch the SQL logs.

## 8. Database & SQL

### 181. Normalization?
Organizing tables to remove duplicate data (1NF, 2NF, 3NF). Store the customer once and reference it by ID.

### 182. Denormalization?
Intentionally duplicating data to make reads faster (e.g., store `CustomerName` in the Orders table for reporting).

### 183. Index?
A sorted structure that speeds up lookups (like a book index). Costs space and slows writes.
`CREATE INDEX IX_Students_Email ON Students(Email);`

### 184. Clustered vs non-clustered?
Clustered: defines the physical row order, only one per table (usually the PK). Non-clustered: separate structure with pointers to rows, many allowed.

### 185. Unique constraint?
Ensures no duplicates in a column (e.g., Email).

### 186. Primary key vs unique key?
PK: one per table, no NULLs, identifies the row. Unique: many per table, usually allows one NULL (SQL Server).

### 187. Foreign key constraint?
Rule enforcing that the value must exist in the parent table, preserving referential integrity.

### 188. Transaction?
See Q177. All-or-nothing unit of work (BEGIN, COMMIT, ROLLBACK).

### 189. ACID?
- **Atomicity**: all or nothing.
- **Consistency**: DB goes from one valid state to another.
- **Isolation**: concurrent transactions don't interfere.
- **Durability**: committed data survives a crash.

### 190. Deadlock?
Two transactions each hold a lock the other needs, so they wait forever. DB kills one (victim). Fix: access tables in the same order, keep transactions short, retry on 1205.

### 191. SQL injection?
Attacker inserts SQL through input: `' OR 1=1 --`.
```csharp
// ❌ dangerous
var sql = "SELECT * FROM Users WHERE Name='" + name + "'";
```

### 192. Preventing SQL injection in .NET?
Use parameters, never concatenate.
```csharp
db.Users.FromSqlInterpolated($"SELECT * FROM Users WHERE Name={name}");
cmd.Parameters.AddWithValue("@name", name);
```
Plus least-privilege DB user and input validation.

### 193. Stored procedure?
Precompiled SQL saved in the DB. `EXEC GetTopStudents @Count = 10`

### 194. Stored procedure vs EF Core LINQ?
SP: close to DB, good for complex reporting/bulk ops, but harder to version/test. LINQ: type-safe, refactorable, testable, portable. Choose LINQ by default, SP for special cases.

### 195. View?
A saved SELECT that behaves like a virtual table. Simplifies complex queries; EF can map entities to views.

### 196. Isolation level?
How much a transaction sees of others' uncommitted/committed changes: Read Uncommitted, Read Committed (default), Repeatable Read, Serializable, Snapshot. Higher = safer, slower.

### 197. Optimistic vs pessimistic locking?
Optimistic: no lock; check version on save (best for web APIs). Pessimistic: lock the row while editing (`UPDLOCK`), safe but blocks others.

### 198. Optimizing a slow SQL query?
1. Check the execution plan. 2. Add proper indexes. 3. Select only needed columns. 4. Avoid `SELECT *` and functions on indexed columns in WHERE. 5. Paginate. 6. Update statistics. 7. Reduce joins/rewrite. 8. Cache.

### 199. What causes DB performance problems in APIs?
Missing indexes, N+1 queries, loading too much data, no paging, long transactions/locks, small connection pools, chatty round trips, unoptimized joins.

### 200. Troubleshooting a slow API caused by DB?
Log SQL (`EnableSensitiveDataLogging` in dev / `LogTo`), find the slow query with Application Insights/Profiler, run it in SSMS with the actual plan, add an index or rewrite, check locks/blocking, check pool exhaustion, re-measure.

## 9. Dependency Injection & Architecture

### 201. DI with a real example
```csharp
public interface INotifier { Task SendAsync(string msg); }
public class EmailNotifier : INotifier { public Task SendAsync(string m) => Task.CompletedTask; }

public class OrderService {
    private readonly INotifier _notifier;
    public OrderService(INotifier n) => _notifier = n;
    public Task PlaceAsync() => _notifier.SendAsync("Order placed");
}
builder.Services.AddScoped<INotifier, EmailNotifier>();
builder.Services.AddScoped<OrderService>();
```
Tomorrow switch to `SmsNotifier` by changing one line.

### 202. Why not use `new` directly?
Tight coupling, can't mock in tests, hard to swap, you manage lifetimes and nested dependencies yourself.

### 203. Constructor injection?
Dependencies passed through the constructor (preferred way): clear, immutable, required dependencies.

### 204. Service registration?
Telling the container which implementation to use for which type (`AddScoped<IFoo, Foo>()`).

### 205. IServiceCollection?
The list of service registrations you add to during startup (`builder.Services`).

### 206. IServiceProvider?
The built container that creates/resolves services at runtime. Avoid using it directly (service locator anti-pattern).

### 207. Service layer?
Layer with business logic between controllers and data access. Controllers stay thin.

### 208. Repository pattern?
An abstraction over data access: `IStudentRepository.GetByIdAsync()`. Hides the persistence details from business code.

### 209. Is it always required with EF Core?
No. `DbContext` is already a repository + unit of work. A repository helps if you need to swap the DB, centralize complex queries, or ease mocking. Many projects skip it for simple CRUD.

### 210. Unit of Work?
Coordinates multiple repositories so they share one transaction and call `SaveChanges` once. (DbContext already is one.)

### 211. Repository vs Unit of Work?
Repository: per-entity data access. UoW: groups changes across repositories into one commit.

### 212. Separation of concerns?
Each part of the code has one job: controller (HTTP), service (business), repository (data).

### 213. Clean Architecture?
Layers with dependencies pointing inward: Domain (entities) ← Application (use cases, interfaces) ← Infrastructure (EF, email) and API (controllers). The business core doesn't depend on frameworks.

### 214. Layered architecture?
Presentation → Business → Data. Each layer calls the one below.

### 215. Onion architecture?
Similar to Clean: domain at the center, with application services, then infrastructure/UI on the outside.

### 216. Clean vs traditional 3-layer?
In 3-layer, business depends on data layer. In Clean, the data layer depends on the business layer's interfaces (dependency inversion), so it's more testable and replaceable.

### 217. Dependency Rule?
Source code dependencies must point inward only. Inner layers know nothing about outer ones.

### 218. SOLID?
Five design principles: **S**ingle Responsibility, **O**pen/Closed, **L**iskov Substitution, **I**nterface Segregation, **D**ependency Inversion.

### 219. Single Responsibility?
A class should have one reason to change.
```csharp
// ❌ OrderService validates, saves, emails, and prints invoice
// ✅ OrderValidator, OrderRepository, EmailSender, InvoicePrinter
```

### 220. Open/Closed?
Open for extension, closed for modification: add new behavior without editing old code.
```csharp
public interface IDiscount { decimal Apply(decimal p); }
public class FestivalDiscount : IDiscount { public decimal Apply(decimal p) => p * 0.9m; }
```
New discount = new class, no `if/else` change.

### 221. Liskov Substitution?
A child must be usable wherever the parent is, without breaking. If `Penguin : Bird` throws on `Fly()`, the design violates LSP.

### 222. Interface Segregation?
Many small interfaces beat one big one. Don't force a class to implement methods it doesn't need (`IReadable`, `IWritable`).

### 223. Dependency Inversion?
High-level code depends on abstractions, not concrete classes. `OrderService` depends on `IPaymentGateway`, not `StripeGateway`.

## 10. Async Programming

### 224. Asynchronous programming?
Starting a long operation (DB, HTTP, file) without blocking the thread; the thread serves other work while waiting.

### 225. Why async/await?
Better scalability (threads not wasted while waiting for I/O), responsive apps, readable code.

### 226. Task?
Represents an ongoing operation that completes later (a "promise").

### 227. Task vs Task<T>?
`Task` = no result. `Task<T>` = produces a result of type T.

### 228. What happens internally on await?
The compiler turns the method into a state machine. At `await`, if the task isn't finished, the method returns to the caller and the thread is freed; when the task completes, the rest (continuation) resumes (on a thread-pool thread in ASP.NET Core).

### 229. async/await vs synchronous?
Sync blocks the thread until done. Async frees it. Async doesn't make a single request faster; it lets the server handle more requests.

### 230. Task.WhenAll()?
Runs tasks concurrently and waits for all.
```csharp
var userTask = GetUserAsync(); var ordersTask = GetOrdersAsync();
await Task.WhenAll(userTask, ordersTask);
```
(Don't use it with one `DbContext` in parallel; it's not thread-safe.)

### 231. WhenAll vs WhenAny?
WhenAll completes when all finish. WhenAny completes when the first finishes (timeouts, "fastest source wins").

### 232. Cancellation token?
An object signaling "stop work". ASP.NET Core passes one that cancels when the client disconnects.

### 233. Cancel an API request?
Accept `CancellationToken ct` in the action and pass it down.
```csharp
[HttpGet] public async Task<IActionResult> Get(CancellationToken ct)
    => Ok(await db.Students.ToListAsync(ct));
```

### 234. CancellationTokenSource?
Creates and triggers tokens.
```csharp
using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(5)); // auto-cancel
await httpClient.GetAsync(url, cts.Token);
```

### 235. Why async for DB calls?
DB calls are I/O-bound. While waiting, the thread returns to the pool, avoiding thread starvation under load.

### 236. `.Result`/`.Wait()` in async code?
They block the thread until the task finishes; can cause deadlocks and thread-pool starvation. Use `await` all the way.

### 237. Async deadlock?
Happens in contexts with a single-threaded SynchronizationContext (UI, old ASP.NET): the caller blocks waiting on `.Result`, while the task needs that same thread to continue. ASP.NET Core has no sync context, but blocking still hurts.

### 238. Can async run on a new thread?
Not necessarily. I/O async uses no thread while waiting. `Task.Run` explicitly queues work to a thread-pool thread (for CPU-bound work).

### 239. ValueTask?
A struct alternative to `Task` that avoids allocation when the result is often available synchronously.

### 240. Task vs ValueTask?
Use `Task` by default. Use `ValueTask<T>` for hot paths that often complete synchronously (e.g., cache hit). Never await a ValueTask twice.

## 11. Authentication & Authorization

### 241. Authentication vs Authorization?
Authentication = **who are you?** (login). Authorization = **what can you do?** (permissions).

### 242. JWT?
JSON Web Token: a signed, compact token carrying claims about the user, sent in `Authorization: Bearer <token>`.

### 243. How does JWT authentication work?
1. User logs in with credentials. 2. Server verifies and issues a signed JWT. 3. Client stores it and sends it with every request. 4. Server validates the signature/expiry and trusts the claims; no session is stored.

### 244. Three parts of a JWT?
`header.payload.signature`, each Base64Url encoded.

### 245. Header?
Metadata: algorithm and type. `{"alg":"HS256","typ":"JWT"}`

### 246. Payload?
The claims: `{"sub":"12","name":"Ali","role":"Admin","exp":1735689600}`. It's encoded, **not encrypted**, so don't put secrets there.

### 247. Signature?
`HMACSHA256(base64(header)+"."+base64(payload), secret)`: proves the token wasn't altered.

### 248. Claim?
A statement about the user (name, email, role, permission).

### 249. Role?
A named group of permissions (Admin, Teacher, Student).

### 250. Role-based vs policy-based authorization?
Role: `[Authorize(Roles="Admin")]`, simple. Policy: flexible rules combining claims/requirements (age > 18, has permission, owns resource).

### 251. [Authorize]?
Requires an authenticated user (optionally with roles/policy) to access the endpoint.

### 252. [AllowAnonymous]?
Allows access without authentication, overriding `[Authorize]` (e.g., login endpoint).

### 253. Configure JWT in ASP.NET Core
```csharp
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
  .AddJwtBearer(o => o.TokenValidationParameters = new() {
      ValidateIssuer = true, ValidIssuer = cfg["Jwt:Issuer"],
      ValidateAudience = true, ValidAudience = cfg["Jwt:Audience"],
      ValidateLifetime = true, ValidateIssuerSigningKey = true,
      IssuerSigningKey = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(cfg["Jwt:Key"])),
      ClockSkew = TimeSpan.FromSeconds(30)
  });
builder.Services.AddAuthorization();
app.UseAuthentication();
app.UseAuthorization();
```
Create a token:
```csharp
var claims = new[] { new Claim(ClaimTypes.NameIdentifier, user.Id.ToString()),
                     new Claim(ClaimTypes.Role, user.Role) };
var creds = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);
var token = new JwtSecurityToken(issuer, audience, claims,
                expires: DateTime.UtcNow.AddMinutes(15), signingCredentials: creds);
return new JwtSecurityTokenHandler().WriteToken(token);
```

### 254. Where should JWT tokens be stored?
Browser: access token in memory; refresh token in an `HttpOnly; Secure; SameSite` cookie. Avoid localStorage (XSS-stealable). Mobile: Keychain/Keystore.

### 255. Access token?
Short-lived token (5-30 min) used to call APIs.

### 256. Refresh token?
Long-lived token used only to obtain new access tokens; stored (hashed) on the server so it can be revoked.

### 257. Access vs refresh token?
| Access | Refresh |
|---|---|
| Short life | Long life |
| Sent to every API | Sent only to the refresh endpoint |
| Stateless | Stored server-side |

### 258. Implement refresh-token authentication?
1. At login, return access + refresh token (random 64-byte string). 2. Save hash(refresh), user, expiry in DB. 3. `POST /auth/refresh` with the refresh token: validate, issue new pair, **rotate** (invalidate the old one). 4. Logout deletes/revokes it.

### 259. Token expiration?
`exp` claim; after it passes, validation fails (401). Short expiry limits the damage of theft.

### 260. Revoke a JWT?
JWTs are stateless, so: keep them short-lived, revoke refresh tokens, keep a deny-list (jti) in Redis, or use a token version/security stamp checked on each request.

### 261. Password hashing?
One-way transformation of a password using a slow algorithm (BCrypt, Argon2, PBKDF2). 
```csharp
var hash = BCrypt.Net.BCrypt.HashPassword(password);
bool ok = BCrypt.Net.BCrypt.Verify(password, hash);
```

### 262. Why not store passwords directly?
If the DB leaks, all passwords are exposed (people reuse them). Hashes can't be reversed.

### 263. Salting?
Adding a unique random value to each password before hashing so identical passwords produce different hashes and rainbow tables fail. BCrypt does it automatically.

### 264. JWT vs session-based?
Session: server stores state (session id in cookie) → easy revoke, harder to scale. JWT: stateless, scalable, good for APIs/microservices, harder to revoke.

### 265. OAuth 2.0 vs JWT?
OAuth 2.0 is an **authorization framework** (how to get tokens). JWT is a **token format**. OAuth can issue JWTs.

### 266. OpenID Connect?
An identity layer on top of OAuth 2.0 that adds authentication (ID token, user info). "Login with Google" uses it.

## 12. REST API Security

### 267. How do you secure a REST API?
HTTPS, authentication + authorization, input validation, CORS rules, rate limiting, hide internal errors, secure headers, secrets management, logging/monitoring, least privilege, up-to-date packages.

### 268. HTTPS?
HTTP over TLS: encrypts traffic and verifies the server identity.

### 269. Why important?
Prevents eavesdropping, tampering, and man-in-the-middle attacks (tokens and passwords stay private).
`app.UseHttpsRedirection(); app.UseHsts();`

### 270. CORS?
Cross-Origin Resource Sharing: a browser rule that blocks JavaScript from calling an API on a different origin unless the API allows it.

### 271. Why does CORS occur?
Because of the Same-Origin Policy. `https://app.com` calling `https://api.com` is cross-origin (different scheme/host/port) and the server's response lacks `Access-Control-Allow-Origin`.

### 272. Configure CORS
```csharp
builder.Services.AddCors(o => o.AddPolicy("Frontend", p =>
    p.WithOrigins("https://app.example.com")
     .AllowAnyHeader().AllowAnyMethod().AllowCredentials()));
app.UseCors("Frontend");   // after UseRouting, before UseAuthentication
```

### 273. CSRF?
Cross-Site Request Forgery: a malicious site makes your browser send an authenticated request (using your cookie) to another site.

### 274. Is CSRF relevant for JWT APIs?
Not if the token is sent in the `Authorization` header (browser doesn't auto-attach it). It **is** relevant if the JWT is stored in cookies; then use SameSite cookies and anti-forgery tokens.

### 275. XSS?
Cross-Site Scripting: attacker injects JavaScript that runs in other users' browsers (steals tokens).

### 276. How can an API protect against XSS?
Validate/sanitize input, encode output, return correct `Content-Type`, set CSP headers, use HttpOnly cookies, never reflect raw input.

### 277. SQL injection?
See Q191/Q192: use parameterized queries/EF.

### 278. Rate limiting?
Restricting how many requests a client can make in a time window.

### 279. Implement in ASP.NET Core (.NET 7+)
```csharp
builder.Services.AddRateLimiter(o => {
    o.RejectionStatusCode = 429;
    o.AddFixedWindowLimiter("api", x => { x.PermitLimit = 100; x.Window = TimeSpan.FromMinutes(1); });
});
app.UseRateLimiter();
app.MapControllers().RequireRateLimiting("api");
```

### 280. Preventing brute-force attacks?
Rate limit login, account lockout after N attempts, CAPTCHA, MFA, slow password hashing, monitor and alert, delay responses.

### 281. API key authentication?
Client sends a secret key in a header (`X-API-Key`) identifying the application.

### 282. API key vs JWT?
API key: identifies an app, simple, long-lived, no user identity. JWT: identifies a user with claims, expires, signed. Use API keys for server-to-server/public partners, JWT for user sessions.

### 283. How should secrets be stored?
Outside the code: user-secrets in dev, environment variables, Key Vault/Secrets Manager in prod. Rotate regularly.

### 284. Why not commit JWT signing keys to GitHub?
Anyone with the key can forge valid tokens (become admin). Public repos are scanned by bots within minutes. If leaked, rotate immediately.

### 285. HTTPS certificate validation?
The client checks the server's certificate is trusted, not expired, and matches the domain. Never disable it (`ServerCertificateCustomValidationCallback = true`) in production.

### 286. Security headers?
HTTP headers that harden browsers: `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `X-Frame-Options`, `Content-Security-Policy`, `Referrer-Policy`.
```csharp
app.Use(async (c, next) => { c.Response.Headers["X-Content-Type-Options"] = "nosniff"; await next(); });
```

## 13. Middleware

### 287. Middleware?
See Q73: components that process requests/responses in a pipeline.

### 288. Middleware pipeline?
An ordered chain. Order matters! Typical order: ExceptionHandler → HTTPS → StaticFiles → Routing → CORS → Authentication → Authorization → Endpoints.

### 289. Use vs Run vs Map?
- `Use`: can call `next()` and pass on.
- `Run`: terminal; ends the pipeline.
- `Map`: branches the pipeline for a path.
```csharp
app.Use(async (c, next) => { await next(); });
app.Map("/health", b => b.Run(c => c.Response.WriteAsync("OK")));
app.Run(c => c.Response.WriteAsync("End"));
```

### 290. Custom middleware
```csharp
public class TimingMiddleware {
    private readonly RequestDelegate _next;
    private readonly ILogger<TimingMiddleware> _log;
    public TimingMiddleware(RequestDelegate next, ILogger<TimingMiddleware> log) { _next = next; _log = log; }
    public async Task InvokeAsync(HttpContext ctx) {
        var sw = Stopwatch.StartNew();
        await _next(ctx);
        _log.LogInformation("{Path} took {Ms}ms", ctx.Request.Path, sw.ElapsedMilliseconds);
    }
}
app.UseMiddleware<TimingMiddleware>();
```

### 291. Where to put exception middleware?
**First** (outermost), so it can catch exceptions from everything after it.

### 292. Authentication middleware placement?
After routing/CORS, before authorization: `UseRouting → UseCors → UseAuthentication → UseAuthorization`.

### 293. Authorization middleware placement?
Right after authentication and before endpoints execute.

### 294. If middleware calls next()?
The request moves on to the next component; code after `next()` runs on the response path.

### 295. If it doesn't call next()?
Pipeline short-circuits; later middleware/endpoint never run (used for auth failures, caching, health checks).

### 296. Can middleware have dependencies?
Yes. Singleton ones via constructor; scoped/transient ones through `InvokeAsync(HttpContext ctx, IMyScopedService svc)` parameters (constructor injection of scoped services is a captive dependency).

### 297. Middleware vs Action Filter?
Middleware: whole pipeline, any request, no MVC knowledge. Filter: only MVC/controller actions, can access ModelState, action arguments and results.

### 298. Middleware vs endpoint filter?
Endpoint filters (minimal APIs) wrap a specific endpoint/group and can see typed arguments. Middleware wraps all requests.

### 299. Request logging middleware
```csharp
app.Use(async (ctx, next) => {
    logger.LogInformation("Req {Method} {Path}", ctx.Request.Method, ctx.Request.Path);
    await next();
    logger.LogInformation("Res {Status}", ctx.Response.StatusCode);
});
```
Or built-in `app.UseHttpLogging();`. Never log secrets or full bodies of sensitive data.

### 300. Global exception middleware
```csharp
public class ExceptionMiddleware(RequestDelegate next, ILogger<ExceptionMiddleware> log) {
    public async Task InvokeAsync(HttpContext ctx) {
        try { await next(ctx); }
        catch (NotFoundException ex) { await Write(ctx, 404, ex.Message); }
        catch (ValidationException ex) { await Write(ctx, 400, ex.Message); }
        catch (Exception ex) { log.LogError(ex, "Unhandled"); await Write(ctx, 500, "Server error"); }
    }
    static Task Write(HttpContext c, int code, string msg) {
        c.Response.StatusCode = code;
        return c.Response.WriteAsJsonAsync(new ProblemDetails { Status = code, Title = msg });
    }
}
```

## 🟡 14. API Design

### 301. Designing REST URLs?
Plural nouns, lowercase, hyphens, hierarchy for relations, no verbs, no file extensions.
```
GET    /api/v1/students
GET    /api/v1/students/5
GET    /api/v1/students/5/courses
POST   /api/v1/students
```

### 302. Why nouns not verbs?
The HTTP method already is the verb. `POST /createStudent` duplicates it; `POST /students` is cleaner and consistent.

### 303. API versioning?
Managing multiple versions of an API so changes don't break existing clients.

### 304. Why needed?
Breaking changes happen (renamed fields, removed endpoints). Old mobile apps keep calling the old contract.

### 305. URL vs header versioning?
URL (`/api/v2/students`): visible, simple, cache-friendly. Header (`X-Api-Version: 2` or media type): cleaner URLs, harder to test in a browser.
```csharp
builder.Services.AddApiVersioning(o => { o.DefaultApiVersion = new ApiVersion(1,0);
    o.AssumeDefaultVersionWhenUnspecified = true; o.ReportApiVersions = true; });
[ApiVersion("1.0")] [Route("api/v{version:apiVersion}/students")]
```

### 306. Backward compatibility?
New API versions keep working for existing clients without modification.

### 307. Breaking change?
Removing/renaming a field or endpoint, changing a type, adding a required parameter, changing status codes/meaning.

### 308. Pagination design?
Return a page plus metadata.
```json
{ "items":[...], "page":2, "pageSize":20, "totalCount":153, "totalPages":8 }
```
`GET /students?page=2&pageSize=20`. Cap pageSize (e.g., 100).

### 309. Offset vs cursor pagination?
Offset: `OFFSET 40 LIMIT 20`. Cursor: "give me 20 items after id=1042".

### 310. Offset vs cursor, which is better?
Offset: simple, jump to page N, but slow on big offsets and unstable if data changes. Cursor: fast and stable at any size, but no random page jumps. Use cursor for feeds/huge tables.
```csharp
var items = await db.Orders.Where(o => o.Id > lastId).OrderBy(o => o.Id).Take(20).ToListAsync();
```

### 311. Filtering?
Query parameters: `GET /products?category=books&minPrice=100`; apply with `if (x != null) q = q.Where(...)`.

### 312. Sorting?
`GET /products?sort=price&order=desc` (whitelist allowed columns!).

### 313. Searching?
`GET /products?search=laptop` using `Contains` / full-text index / Elasticsearch for large data.

### 314. Pagination + filtering + sorting together
```csharp
public async Task<PagedResult<ProductDto>> GetAsync(ProductQuery q) {
    IQueryable<Product> query = db.Products.AsNoTracking();
    if (!string.IsNullOrWhiteSpace(q.Search)) query = query.Where(p => p.Name.Contains(q.Search));
    if (q.Category != null) query = query.Where(p => p.Category == q.Category);
    query = q.Sort switch {
        "price" => q.Desc ? query.OrderByDescending(p => p.Price) : query.OrderBy(p => p.Price),
        _       => query.OrderBy(p => p.Id) };
    var total = await query.CountAsync();
    var items = await query.Skip((q.Page - 1) * q.PageSize).Take(q.PageSize)
                           .Select(p => new ProductDto(p.Id, p.Name, p.Price)).ToListAsync();
    return new PagedResult<ProductDto>(items, total, q.Page, q.PageSize);
}
```

### 315. HATEOAS?
Responses include links to related actions so clients discover them.
```json
{ "id":5, "status":"Pending", "links":[{"rel":"cancel","href":"/orders/5/cancel","method":"POST"}] }
```

### 316. API discoverability?
How easily clients can find what the API offers: OpenAPI/Swagger docs, links in responses, consistent naming.

### 317. Idempotency key?
A unique client-generated ID (header `Idempotency-Key: uuid`) so the server recognizes repeat attempts of the same POST.

### 318. When to use it?
Payments, order creation, anything where retrying a POST must not duplicate (see Q561).

### 319. Request/response contract?
The agreed shape of requests and responses: fields, types, status codes, errors. Documented with OpenAPI.

### 320. Backward-compatible API evolution?
Only add optional fields/endpoints, never remove/rename; keep old fields until a deprecation period ends; ignore unknown fields; version when breaking.

## 15. DTOs & Mapping

### 321. DTO?
See Q149: a simple object shaping data in/out of the API.

### 322. Why not return EF entities?
Leaks sensitive fields, exposes DB structure, causes JSON cycles (`Order → Customer → Orders`), over-posting risk, tight coupling, loads unnecessary data.

### 323. Entity vs DTO?
Entity = database model with relations and tracking. DTO = API contract, flat, only needed fields.

### 324. Request DTO vs Response DTO?
Request DTO: what the client sends (no `Id`, no `CreatedAt`). Response DTO: what you return (includes `Id`, computed fields, no password).
```csharp
public record CreateStudentRequest(string Name, string Email);
public record StudentResponse(int Id, string Name, string Email, DateTime CreatedAt);
```

### 325. AutoMapper?
Library that maps one object type to another by convention.
```csharp
public class StudentProfile : Profile { public StudentProfile() => CreateMap<Student, StudentResponse>(); }
var dto = mapper.Map<StudentResponse>(student);
```

### 326. AutoMapper vs manual mapping?
AutoMapper: less code, but "magic", runtime errors, harder to debug. Manual (or Mapperly source generator): explicit, compile-time safe, fastest.

### 327. Problems AutoMapper can cause?
Hidden mapping errors found at runtime, silent null/default values, performance hits in `ProjectTo` misuse, tricky debugging, unintended lazy-loading triggers, licensing changes in newer versions.

### 328. Preventing sensitive properties from being returned?
Use response DTOs without those fields, `[JsonIgnore]` as a backup, project with `Select`, and write tests that assert the JSON doesn't contain `PasswordHash`.

### 329. Nested DTOs?
```csharp
public record OrderResponse(int Id, CustomerDto Customer, List<OrderItemDto> Items);
db.Orders.Select(o => new OrderResponse(o.Id,
    new CustomerDto(o.Customer.Id, o.Customer.Name),
    o.Items.Select(i => new OrderItemDto(i.ProductName, i.Qty)).ToList()));
```

### 330. Mapping collections?
`mapper.Map<List<StudentResponse>>(students)` or `students.Select(ToDto).ToList()` or `ProjectTo<T>()` directly in the EF query.

## 16. Validation

### 331. Data validation?
Checking that input is correct in format, range, and required-ness before using it.

### 332. Data Annotation validation?
Attributes on DTO properties.
```csharp
public class CreateStudentRequest {
    [Required, StringLength(100)] public string Name { get; set; }
    [Required, EmailAddress] public string Email { get; set; }
    [Range(5, 100)] public int Age { get; set; }
}
```

### 333. FluentValidation?
Library to write rules in a separate, readable class.
```csharp
public class CreateStudentValidator : AbstractValidator<CreateStudentRequest> {
    public CreateStudentValidator() {
        RuleFor(x => x.Name).NotEmpty().MaximumLength(100);
        RuleFor(x => x.Email).NotEmpty().EmailAddress();
        RuleFor(x => x.Age).InclusiveBetween(5, 100);
    }
}
```

### 334. FluentValidation vs Data Annotations?
Annotations: quick, built-in, limited. FluentValidation: complex/conditional rules, async checks, testable, DTO stays clean.

### 335. How does [ApiController] handle validation?
Before the action runs it checks `ModelState`; if invalid it automatically returns `400` with a `ValidationProblemDetails` body.

### 336. Returning validation errors?
```json
{ "title":"One or more validation errors occurred.","status":400,
  "errors":{ "Email":["The Email field is not a valid e-mail address."] } }
```
Manually: `return ValidationProblem(ModelState);`

### 337. Custom validation?
```csharp
public class FutureDateAttribute : ValidationAttribute {
    protected override ValidationResult IsValid(object v, ValidationContext c)
        => v is DateTime d && d > DateTime.UtcNow ? ValidationResult.Success : new("Date must be in future");
}
```
Or implement `IValidatableObject`, or a FluentValidation `.Must(...)`.

### 338. Business validation?
Rules based on application state/domain: "Email already registered", "Insufficient stock", "Course is full".

### 339. Data vs business validation?
Data: shape of the input, doesn't need the DB (required, length). Business: needs data/state, done in the service layer (returns 409/422).

### 340. Validating a complex nested request?
Use child validators.
```csharp
RuleFor(x => x.Customer).SetValidator(new CustomerValidator());
RuleForEach(x => x.Items).SetValidator(new OrderItemValidator());
RuleFor(x => x.Items).NotEmpty();
```

## 17. Logging & Monitoring

### 341. Logging?
Recording what the app does (events, errors) to diagnose problems.

### 342. ILogger<T>?
Built-in logger injected per class; `T` becomes the category name.
```csharp
public class StudentService(ILogger<StudentService> log) {
    void Do() => log.LogInformation("Student {StudentId} created", 5);
}
```

### 343-344. Log levels? Trace vs Debug vs Information vs Warning vs Error vs Critical?
| Level | Use |
|---|---|
| Trace | Very detailed, dev only |
| Debug | Debug info during development |
| Information | Normal flow (request handled, order created) |
| Warning | Unexpected but app continues (retry, slow call) |
| Error | Operation failed (exception caught) |
| Critical | App-wide failure (DB down, out of memory) |

### 345. Why structured logging?
Logs keep named properties (`{OrderId}`), so you can search/filter (Serilog + Seq/Elastic) rather than parse text.
`log.LogInformation("Order {OrderId} paid {Amount}", id, amt);` (not string interpolation)

### 346. What should never be logged?
Passwords, tokens, API keys, credit card numbers, personal data (PII), health data, full request bodies with secrets.

### 347. Correlation ID?
A unique ID attached to a request and passed to every log/service it touches.

### 348. Why useful?
You can find all log lines for one request across layers/services and trace failures.

### 349. Trace one request across services?
Generate/forward `X-Correlation-Id` (or W3C `traceparent`), include in logs, use OpenTelemetry + Jaeger/Zipkin/App Insights.
```csharp
app.Use(async (ctx, next) => {
    var id = ctx.Request.Headers["X-Correlation-Id"].FirstOrDefault() ?? Guid.NewGuid().ToString();
    ctx.Response.Headers["X-Correlation-Id"] = id;
    using (logger.BeginScope(new Dictionary<string, object> { ["CorrelationId"] = id })) await next();
});
```

### 350. Health checking?
An endpoint reporting whether the app and its dependencies work.

### 351. Liveness check?
"Is the process alive?" If not, restart it (Kubernetes livenessProbe).

### 352. Readiness check?
"Can it serve traffic now?" (DB reachable, caches warm). If not, remove from load balancer without restarting.

### 353. Health checks in ASP.NET Core
```csharp
builder.Services.AddHealthChecks()
    .AddSqlServer(conn, tags: new[] { "ready" })
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: new[] { "live" });
app.MapHealthChecks("/health/live",  new() { Predicate = r => r.Tags.Contains("live") });
app.MapHealthChecks("/health/ready", new() { Predicate = r => r.Tags.Contains("ready") });
```

## 🟡 18. Testing

### 354. Unit testing?
Testing one small unit (method/class) in isolation with dependencies faked.

### 355. Integration testing?
Testing several parts together (API + real/test DB + middleware).

### 356. Unit vs integration?
Unit: fast, many, isolated. Integration: slower, fewer, confirms components work together. Follow the testing pyramid.

### 357. xUnit?
Popular .NET test framework (`[Fact]`, `[Theory]`), new instance per test.

### 358. NUnit?
Another framework (`[Test]`, `[TestCase]`, `[SetUp]`), similar purpose.

### 359. Mocking?
Replacing real dependencies with fake objects whose behavior you control and verify.

### 360. Moq?
Library to create mocks.
```csharp
var repo = new Mock<IStudentRepository>();
repo.Setup(r => r.GetByIdAsync(1)).ReturnsAsync(new Student { Id = 1, Name = "Ali" });
var service = new StudentService(repo.Object);
var result = await service.GetAsync(1);
Assert.Equal("Ali", result.Name);
repo.Verify(r => r.GetByIdAsync(1), Times.Once);
```

### 361. What should be mocked?
External boundaries: databases, HTTP clients, email/SMS, file system, clock, message brokers.

### 362. What shouldn't be mocked?
Simple value objects, the class under test, pure logic, DTOs, language/framework types (`List<T>`). Don't mock what you own deeply; use a real in-memory/test DB for repository tests.

### 363. Test a controller?
Create the controller with a mocked service and assert the result type.
```csharp
var result = await controller.Get(99);
Assert.IsType<NotFoundResult>(result.Result);
```

### 364. Test a service?
Mock its dependencies, call the method, assert outputs and interactions, including failure cases.

### 365. Test an API endpoint?
Use `WebApplicationFactory` and `HttpClient` to call the real pipeline.

### 366. WebApplicationFactory?
Hosts your app in memory for tests.
```csharp
public class StudentApiTests : IClassFixture<WebApplicationFactory<Program>> {
    private readonly HttpClient _client;
    public StudentApiTests(WebApplicationFactory<Program> f) => _client = f.CreateClient();
    [Fact] public async Task Get_ReturnsOk() {
        var res = await _client.GetAsync("/api/students");
        Assert.Equal(HttpStatusCode.OK, res.StatusCode);
    }
}
```
(Add `public partial class Program { }` for top-level programs.)

### 367. Integration test database?
A separate DB for tests: SQLite in-memory, EF InMemory (limited), or best: real SQL Server/Postgres in a Testcontainers Docker container.

### 368. Test isolation?
Each test runs independently with its own data/state, so order and parallelism don't matter (reset DB, transactions, unique data).

### 369. Code coverage?
Percentage of code executed by tests. Useful guide, but 100% coverage doesn't mean good tests.

### 370. What makes a good unit test?
Fast, isolated, repeatable, self-validating, readable (Arrange-Act-Assert), tests one behavior, clear name (`Method_Condition_Expected`).

# 🔴 LEVEL 3: HARD / ADVANCED

## 19. Advanced ASP.NET Core

### 371. Complete lifecycle of an HTTP request?
1. Client sends request. 2. Kestrel (via reverse proxy) receives it and creates `HttpContext`. 3. Middleware pipeline runs in order. 4. Endpoint routing selects the endpoint. 5. Authentication/authorization. 6. Model binding + validation. 7. Filters → action executes (DI resolves services in a request scope). 8. Result is serialized. 9. Response flows back through middleware. 10. Scope disposed, response sent.

### 372. Middleware pipeline internally?
It's a chain of `RequestDelegate` functions. `app.Use(...)` wraps the next delegate; the builder composes them in reverse order into one delegate that Kestrel invokes per request.

### 373. How does DI resolve services?
The container finds the registration for the requested type, checks its lifetime (cache for singleton/scoped), recursively resolves constructor parameters (picks the constructor it can satisfy), builds the instance (compiled expressions), and tracks `IDisposable` ones for disposal.

### 374. Scoped service injected into a singleton?
The scoped service lives as long as the singleton (becomes effectively singleton). In Development, `ValidateScopes` throws an error.

### 375. Captive dependency?
A longer-lived service holding a shorter-lived one (singleton → scoped DbContext).

### 376. Problems it causes?
Stale data, DbContext used across threads (not thread-safe → random exceptions), memory leaks, wrong user data leaks between requests.
Fix: inject `IServiceScopeFactory` and create a scope.
```csharp
using var scope = _scopeFactory.CreateScope();
var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
```

### 377. Application lifetime?
`IHostApplicationLifetime` exposes `ApplicationStarted`, `ApplicationStopping`, `ApplicationStopped` and `StopApplication()`. The Host starts hosted services, runs, and stops them on SIGTERM/Ctrl+C.

### 378. Hosted services?
Long-running background tasks managed by the host (`IHostedService`).

### 379. BackgroundService?
Abstract base class implementing `IHostedService`; you override `ExecuteAsync`.

### 380. IHostedService vs BackgroundService?
`IHostedService`: you write Start/Stop yourself. `BackgroundService`: simplified single `ExecuteAsync` loop with cancellation. Use BackgroundService for most cases.

### 381. Implement a background job
```csharp
public class EmailQueueWorker(IServiceScopeFactory sf, ILogger<EmailQueueWorker> log) : BackgroundService {
    protected override async Task ExecuteAsync(CancellationToken ct) {
        while (!ct.IsCancellationRequested) {
            using var scope = sf.CreateScope();
            var svc = scope.ServiceProvider.GetRequiredService<IEmailService>();
            try { await svc.ProcessPendingAsync(ct); }
            catch (Exception ex) { log.LogError(ex, "Worker failed"); }
            await Task.Delay(TimeSpan.FromSeconds(10), ct);
        }
    }
}
builder.Services.AddHostedService<EmailQueueWorker>();
```
For persistent/scheduled jobs use Hangfire or Quartz.NET.

### 382. Graceful shutdown?
On SIGTERM the host stops accepting new requests, waits for in-flight requests and hosted services up to `ShutdownTimeout` (default 30s), then exits.
`builder.Services.Configure<HostOptions>(o => o.ShutdownTimeout = TimeSpan.FromSeconds(30));`

### 383. Active requests during shutdown?
Kestrel finishes them within the timeout; remaining ones get aborted. Pass `CancellationToken` so work can stop cleanly. Load balancer should stop sending traffic first (readiness fails).

### 384. Endpoint routing?
Routing selected early (`UseRouting`) so middleware in between (auth, CORS) knows which endpoint will run and its metadata.

### 385. How does it work internally?
At startup endpoints are collected into a graph/matcher (DFA). `UseRouting` matches the URL and sets the selected endpoint on `HttpContext`; `UseEndpoints` (or implicit in .NET 6+) executes it.

### 386. Endpoint filters?
Minimal API filters running before/after the handler with access to arguments.
```csharp
app.MapPost("/students", (CreateStudent r) => ...)
   .AddEndpointFilter(async (ctx, next) => { /* validate */ return await next(ctx); });
```

### 387. Endpoint filters vs middleware vs action filters?
Middleware: all requests, generic. Action filters: MVC controllers. Endpoint filters: minimal API handlers. Choose by scope.

### 388. Minimal API?
Lightweight way to define endpoints without controllers.
```csharp
app.MapGet("/students/{id}", async (int id, AppDbContext db) =>
    await db.Students.FindAsync(id) is { } s ? Results.Ok(s) : Results.NotFound());
```

### 389. Minimal vs controller?
Minimal: less ceremony, faster startup, great for microservices; Controllers: more features (filters, conventions, versioning), better for big structured APIs.

### 390. When choose Minimal APIs?
Small services, microservices, quick prototypes, serverless, when you want AOT and low overhead. Organize with route groups and extension methods.

## 20. Advanced EF Core

### 391. EF change tracking internally?
`DbContext` has a `ChangeTracker` holding `InternalEntityEntry` per tracked entity with a snapshot of original values and a state (`Added, Unchanged, Modified, Deleted, Detached`). On `SaveChanges` it compares and creates commands.

### 392. Tracked vs untracked queries?
Tracked: entities stored in the tracker, changes saved, identity resolved. Untracked: plain objects, faster, no saving.

### 393. How does EF detect changes?
`DetectChanges()` compares current values with the snapshot (or uses `INotifyPropertyChanged` / change-tracking proxies). It runs at `SaveChanges` and some tracker operations.

### 394. Identity resolution?
Ensures a single object instance per primary key in the context: loading the same row twice gives the same object.

### 395. AsNoTrackingWithIdentityResolution()?
No tracking, but still uses one instance per key within the query results (avoids duplicate objects in graphs with shared references, slower than plain AsNoTracking).

### 396. Query projection?
Using `Select` to fetch only needed columns into a DTO.
`db.Students.Select(s => new StudentDto(s.Id, s.Name))`

### 397. Why is projection better?
Less data read/transferred, no tracking, smaller SQL, avoids loading unused navigation properties, doesn't need `Include`.

### 398. Optimize EF queries?
`AsNoTracking`, projection, filter early, indexes, paging, avoid N+1, split queries, compiled queries, `ExecuteUpdate/Delete`, `AnyAsync` instead of Count, avoid client evaluation, batch operations.

### 399. Compiled query?
Pre-compiles the LINQ → SQL translation for reuse.
```csharp
static readonly Func<AppDbContext,int,Task<Student?>> GetById =
    EF.CompileAsyncQuery((AppDbContext db, int id) => db.Students.FirstOrDefault(s => s.Id == id));
```

### 400. Split query?
`AsSplitQuery()` runs one SQL per included collection instead of one giant JOIN.

### 401. Single vs split?
Single: one round trip, consistent snapshot, but Cartesian explosion risk. Split: smaller result sets, multiple round trips, possible inconsistency between queries.

### 402. How can Include() cause performance problems?
Joining multiple collections multiplies rows, loading huge graphs, loading unneeded columns, and tracking cost.

### 403. Cartesian explosion?
Joining two or more collections: 100 items × 50 comments = 5,000 duplicated rows returned.

### 404. Preventing it?
Use `AsSplitQuery()`, projection, load collections separately, or limit includes. Configure `UseQuerySplittingBehavior(SplitQuery)` globally.

### 405. Optimistic concurrency in EF Core?
See Q176: `[Timestamp]`/`IsRowVersion` or `IsConcurrencyToken()`. `UPDATE ... WHERE Id=@id AND RowVersion=@old`; 0 rows affected → exception.

### 406. Handle concurrency conflicts?
```csharp
try { await db.SaveChangesAsync(); }
catch (DbUpdateConcurrencyException ex) {
    var entry = ex.Entries.Single();
    var dbValues = await entry.GetDatabaseValuesAsync();
    // options: client wins (entry.OriginalValues.SetValues(dbValues)), db wins (reload),
    // or merge. For APIs: return 409 Conflict / 412 Precondition Failed.
}
```

### 407. Soft delete?
Mark `IsDeleted = true` instead of removing the row, then hide it with a global filter.
```csharp
modelBuilder.Entity<Student>().HasQueryFilter(s => !s.IsDeleted);
// bypass: db.Students.IgnoreQueryFilters()
```
Intercept `SaveChanges` to convert `Deleted` → `Modified` with `IsDeleted = true`.

### 408. Global query filters?
LINQ predicates applied automatically to every query for an entity (soft delete, multi-tenant `TenantId == current`).

### 409. Interceptors?
Hooks to intercept EF operations (`SaveChangesInterceptor`, `DbCommandInterceptor`, `DbConnectionInterceptor`) for auditing, logging SQL, adding hints.

### 410. Audit database changes?
```csharp
public class AuditInterceptor : SaveChangesInterceptor {
    public override ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData e, InterceptionResult<int> r, CancellationToken ct = default) {
        foreach (var entry in e.Context!.ChangeTracker.Entries<IAuditable>()) {
            if (entry.State == EntityState.Added)    entry.Entity.CreatedAt = DateTime.UtcNow;
            if (entry.State == EntityState.Modified) entry.Entity.UpdatedAt = DateTime.UtcNow;
        }
        return base.SavingChangesAsync(e, r, ct);
    }
}
```
For full history store old/new values in an `AuditLog` table, or use temporal tables.

### 411. Execute raw SQL safely?
Use parameterized APIs.
```csharp
db.Students.FromSql($"SELECT * FROM Students WHERE City = {city}");
await db.Database.ExecuteSqlInterpolatedAsync($"UPDATE Students SET Active=0 WHERE Id={id}");
```
Never `FromSqlRaw` with string concatenation.

### 412. ExecuteUpdate()?
Bulk UPDATE in the DB without loading entities (EF Core 7+).
`await db.Products.Where(p => p.Category=="Book").ExecuteUpdateAsync(s => s.SetProperty(p => p.Price, p => p.Price * 1.1m));`

### 413. ExecuteDelete()?
Bulk DELETE directly: `await db.Logs.Where(l => l.Date < cutoff).ExecuteDeleteAsync();`

### 414. How do bulk operations affect change tracking?
They bypass it: tracked entities in memory aren't updated, interceptors/`SaveChanges` logic (audit, soft delete) don't run, and they execute immediately (not batched with `SaveChanges`) unless wrapped in a transaction.

### 415. Transaction across multiple repositories?
Share one `DbContext` (scoped) so one `SaveChanges` covers all, or use Unit of Work with an explicit transaction.
```csharp
await using var tx = await _uow.BeginTransactionAsync();
await _orders.AddAsync(order);
await _inventory.ReduceAsync(order.Items);
await _uow.SaveChangesAsync();
await tx.CommitAsync();
```
Across databases/services use Saga/Outbox, not a single transaction.

## 21. Advanced REST API

### 416. What makes an API truly RESTful?
It follows all REST constraints, including HATEOAS (hypermedia links). Most "REST" APIs are really Level 2 of the maturity model.

### 417. REST constraints?
1. **Client-server** separation. 2. **Stateless**. 3. **Cacheable**. 4. **Uniform interface** (resources, representations, self-descriptive messages, HATEOAS). 5. **Layered system**. 6. Code on demand (optional).

### 418. Richardson Maturity Model?
A scale measuring how RESTful an API is (Levels 0-3).

### 419. Level 0 vs 1 vs 2 vs 3?
| Level | Meaning | Example |
|---|---|---|
| 0 | One URL, one method (RPC over HTTP) | `POST /api` with action in body |
| 1 | Multiple resources/URLs | `POST /students/5/getMarks` |
| 2 | + correct HTTP verbs and status codes | `GET /students/5` → 200/404 |
| 3 | + HATEOAS links | response includes `links` |

### 420. Resource-oriented design?
Model the API around things (resources) with consistent URLs and standard methods instead of operations/functions.

### 421. Nested resources?
Show parent-child relationships: `GET /customers/10/orders`, `GET /orders/55/items`.

### 422. When avoid nesting?
When it goes deeper than 2 levels, or the child has its own identity. Prefer `GET /orders/55` + filter `GET /orders?customerId=10` over `/customers/10/orders/55/items/3/...`.

### 423. APIs for very large datasets?
Cursor pagination, filtering, streaming (`IAsyncEnumerable`), compression, field selection, async export jobs (return 202 + job URL), read replicas, caching, indexes.

### 424. High-volume POST API?
Validate quickly, accept and enqueue (message queue), return `202 Accepted`, process asynchronously with workers, batch inserts, idempotency keys, rate limits, partition data.

### 425. Making POST idempotent?
Client sends `Idempotency-Key`. Server stores key + response; if the key repeats, return the stored response without redoing the work.
```csharp
[HttpPost]
public async Task<IActionResult> Create([FromHeader(Name="Idempotency-Key")] string key, CreateOrder dto) {
    var existing = await _store.GetAsync(key);
    if (existing != null) return StatusCode(existing.Status, existing.Body);
    var result = await _orders.CreateAsync(dto);
    await _store.SaveAsync(key, 201, result);   // unique index on key
    return Created($"/api/orders/{result.Id}", result);
}
```

### 426. Handling duplicate requests?
Idempotency keys, unique DB constraints (business key), de-duplication cache (Redis `SET NX` with TTL), natural idempotent design (PUT), and disable the double-click on the UI.

### 427. Supporting millions of users?
Stateless API behind a load balancer, horizontal scaling, caching (CDN + Redis), DB read replicas/sharding, async processing with queues, rate limiting, pagination, monitoring + autoscaling.

### 428. Preventing API abuse?
Rate limiting/throttling, authentication, quotas per key, WAF, IP blocking, request size limits, captcha, anomaly monitoring, API gateway.

### 429. Handling backward compatibility?
Additive changes only, version when breaking, tolerant readers, contract tests, deprecation policy.

### 430. Safely deprecate a version?
Announce a timeline, add `Deprecation`/`Sunset` headers, document migration, monitor usage per version, contact remaining clients, return warnings, then remove (410 Gone).

### 431. Optimistic concurrency at API level?
Return an `ETag` (version). Clients send it back with `If-Match` on update. If it doesn't match the current version → `412 Precondition Failed`.

### 432. Preventing lost updates?
Optimistic concurrency (ETag/RowVersion), or pessimistic lock for critical cases, or atomic updates (`UPDATE ... SET qty = qty - 1 WHERE qty > 0`).

### 433. ETags?
An identifier of a specific version of a resource (hash/version), sent in the `ETag` header.

### 434. How do ETag and If-Match work?
```
GET /students/5      → 200, ETag: "v7"
PUT /students/5      If-Match: "v7"
  server: current version is "v7" → update, return new ETag "v8"
  server: current is "v8"          → 412 Precondition Failed
```
`If-None-Match` is the opposite, for caching: unchanged → `304 Not Modified`.

### 435. Conditional requests?
```csharp
var etag = $"\"{student.RowVersionBase64}\"";
if (Request.Headers.IfNoneMatch == etag) return StatusCode(304);
Response.Headers.ETag = etag;
return Ok(student);
```

### 436. HTTP caching?
Reusing earlier responses (browser, proxy, CDN) to avoid hitting the server, controlled by headers (`Cache-Control`, `ETag`, `Last-Modified`).

### 437. Cache-Control vs ETag?
`Cache-Control` says **how long** a response may be reused (`max-age=60`). ETag lets the client **validate** whether its cached copy is still current (cheap 304). They work together.

### 438. Cache invalidation?
Removing/updating cached data when the source changes. Methods: TTL expiry, explicit eviction on update, versioned keys, event-based invalidation, `Cache-Control: no-cache`. "One of the hardest problems."

### 439. Content negotiation?
See Q120. In ASP.NET Core: `AddControllers(o => o.RespectBrowserAcceptHeader = true).AddXmlSerializerFormatters()`; `[Produces("application/json")]`.

### 440. Support multiple response formats?
Add formatters (JSON, XML, CSV via custom `OutputFormatter`), honor `Accept` header, return 406 if unsupported, optionally allow `?format=csv`.

## 22. Advanced Authentication & Security

### 441. Complete JWT authentication flow
1. `POST /auth/login` with credentials. 2. Server verifies password hash. 3. Creates claims, signs JWT (+ refresh token). 4. Client stores and sends `Authorization: Bearer`. 5. Middleware validates signature, issuer, audience, expiry. 6. Claims become `HttpContext.User`. 7. `[Authorize]` checks roles/policies. 8. On expiry client calls `/auth/refresh`.

### 442. How does ASP.NET Core validate a JWT?
`JwtBearerHandler` reads the header, parses the token, `TokenValidationParameters` checks signature (key), issuer, audience, lifetime (`nbf`/`exp`, clock skew), builds a `ClaimsPrincipal`, and fires events (`OnTokenValidated`).

### 443. Invalid signature?
Token rejected (tampered or wrong key) → `401 Unauthorized` with `WWW-Authenticate: Bearer error="invalid_token"`.

### 444. Expired JWT?
Rejected → 401 (`The token expired at ...`). The client should use its refresh token.

### 445. Refresh-token rotation?
Each refresh call issues a **new** refresh token and invalidates the old one; every refresh token is single-use.

### 446. Detecting refresh-token reuse?
If an already-used token arrives again, someone stole it. Reaction: revoke the whole token family/chain for that user and force re-login.
```csharp
var stored = await db.RefreshTokens.SingleOrDefaultAsync(t => t.TokenHash == hash);
if (stored.IsUsed) { await RevokeFamilyAsync(stored.FamilyId); return Unauthorized(); }
stored.IsUsed = true;   // then issue a new one in the same family
```

### 447. Revoke refresh tokens?
Set `RevokedAt` in DB on logout, password change, or suspicious activity; delete expired tokens with a cleanup job.

### 448. Securing JWT against theft?
Short access-token life, HTTPS only, HttpOnly/Secure/SameSite cookies, rotation, bind tokens to device/IP fingerprints, CSP to reduce XSS, don't store in localStorage, revoke on logout, monitor anomalies.

### 449. Where to store refresh tokens?
Browser: HttpOnly Secure SameSite cookie. Mobile: Keychain/Keystore. Server side: only the **hash** in DB.

### 450. Token rotation?
Regularly replacing credentials (refresh tokens on each use, signing keys on schedule using `kid` header to support old + new keys).

### 451. OAuth 2.0 Authorization Code Flow?
1. App redirects user to auth server. 2. User logs in and consents. 3. Auth server redirects back with a one-time **code**. 4. App's backend exchanges code (+ client secret/PKCE verifier) for tokens. Safe because tokens never travel through the browser URL.

### 452. PKCE?
Proof Key for Code Exchange: client creates a random `code_verifier`, sends its hash (`code_challenge`) first, and later sends the original verifier when exchanging the code.

### 453. Why important?
It stops attackers who steal the authorization code from exchanging it (they don't have the verifier). Required for SPAs/mobile apps that can't keep a secret; recommended for all clients.

### 454. OAuth 2.0 vs OpenID Connect?
OAuth 2.0 = authorization (access to APIs). OIDC = authentication (who the user is; adds ID token, `openid` scope, userinfo).

### 455. IdentityServer / OpenIddict?
Libraries to build your own OAuth 2.0/OIDC authorization server (issue tokens, SSO, federation). Use when you need central login for many apps. (Alternatives: Keycloak, Auth0, Entra ID.) Note Duende IdentityServer needs a commercial license.

### 456. Authentication vs authorization at middleware level?
`UseAuthentication()` identifies the user and sets `HttpContext.User`. `UseAuthorization()` then checks policies on the selected endpoint. Authentication must run first.

### 457. Policy-based vs role-based?
See Q250. Policies scale better: "CanEditStudent" instead of dozens of role combinations.
```csharp
builder.Services.AddAuthorization(o => o.AddPolicy("AdultOnly", p => p.RequireClaim("age").RequireAssertion(c => ...)));
[Authorize(Policy = "AdultOnly")]
```

### 458. Custom authorization handlers?
```csharp
public record MinimumAgeRequirement(int Age) : IAuthorizationRequirement;
public class MinimumAgeHandler : AuthorizationHandler<MinimumAgeRequirement> {
    protected override Task HandleRequirementAsync(AuthorizationHandlerContext ctx, MinimumAgeRequirement req) {
        var dob = DateTime.Parse(ctx.User.FindFirst("dob")!.Value);
        if (DateTime.Today.Year - dob.Year >= req.Age) ctx.Succeed(req);
        return Task.CompletedTask;
    }
}
services.AddSingleton<IAuthorizationHandler, MinimumAgeHandler>();
services.AddAuthorization(o => o.AddPolicy("Adult", p => p.AddRequirements(new MinimumAgeRequirement(18))));
```
Resource-based: inject `IAuthorizationService` and call `AuthorizeAsync(User, order, "OwnerPolicy")`.

### 459. Permission-based authorization?
Store permissions like `students.read`, `students.delete` per role in DB; put them in token claims (or load from cache) and use a policy provider.
```csharp
public class PermissionAttribute(string perm) : AuthorizeAttribute($"Permission:{perm}");
// Dynamic IAuthorizationPolicyProvider + PermissionHandler checks user permission claims
[Permission("students.delete")]
[HttpDelete("{id}")] public Task<IActionResult> Delete(int id) { ... }
```
Tables: `Users`, `Roles`, `Permissions`, `RolePermissions`, `UserRoles`.

### 460. Securing service-to-service communication?
mTLS, OAuth 2.0 **client credentials** flow (service gets a token), private network/service mesh, API gateway, short-lived tokens, secret rotation, managed identities in cloud.

## 23. Performance & Scalability

### 461. Improve ASP.NET Core API performance?
Async I/O everywhere, `AsNoTracking`, projection, indexes, pagination, caching, response compression, connection pooling, avoid N+1, `HttpClientFactory`, minimal allocations (`Span`), keep middleware light, use latest .NET, profile first.

### 462. Identify a slow endpoint?
APM tools (Application Insights, OpenTelemetry), request duration logs, `dotnet-trace`/`dotnet-counters`, EF SQL logs, load tests (k6, JMeter), percentile metrics (p95/p99).

### 463. What causes high latency?
Slow queries, N+1, no cache, external API calls, thread pool starvation (sync over async), large payloads, GC pauses, network distance, cold starts, lock contention.

### 464. Reduce DB round trips?
Eager load/projection, batch commands, `WhenAll` on separate contexts for independent reads, caching, stored procedures for multi-step logic, bulk operations.

### 465. Response caching?
Storing whole HTTP responses so repeated GETs are served quickly: `[ResponseCache(Duration=60)]`, `AddResponseCaching()`, or Output Caching in .NET 7+ (`app.UseOutputCache()`).

### 466. Distributed caching?
A cache shared by all app instances (Redis, SQL Server) via `IDistributedCache`.

### 467. In-memory vs distributed cache?
In-memory (`IMemoryCache`): fastest, per-server, lost on restart, inconsistent across instances. Distributed: shared, consistent, survives restarts, network latency.

### 468. Redis?
Fast in-memory key-value store supporting strings, hashes, lists, sets, TTL, pub/sub, locks.

### 469. When use Redis?
Caching, session/token deny-lists, rate limiting counters, distributed locks, leaderboards, pub/sub.

### 470. Cache-aside pattern?
App checks cache first; on miss loads from DB and stores in cache.
```csharp
public async Task<StudentDto?> GetAsync(int id) {
    var key = $"student:{id}";
    var cached = await _cache.GetStringAsync(key);
    if (cached != null) return JsonSerializer.Deserialize<StudentDto>(cached);
    var dto = await _repo.GetDtoAsync(id);
    if (dto != null) await _cache.SetStringAsync(key, JsonSerializer.Serialize(dto),
        new DistributedCacheEntryOptions { AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5) });
    return dto;
}
```
On update: delete the key.

### 471. Cache stampede?
A popular key expires and thousands of requests miss at once, all hitting the DB.

### 472. Preventing it?
Locking/single-flight (only one request rebuilds), randomized TTL (jitter), early refresh/background refresh, serve stale while revalidating, `HybridCache` (.NET 9) that coalesces requests.

### 473. Connection pooling?
Reusing open DB connections instead of creating a new one per query.

### 474. How does it work?
`SqlConnection.Open()` takes a connection from the pool (same connection string); `Close()/Dispose()` returns it. Default max 100. Leaks (not disposing) → "timeout expired: pool exhausted". Always `await using`/DI scoped DbContext.

### 475. Horizontal scaling?
Add more servers/instances behind a load balancer.

### 476. Vertical scaling?
Make one server bigger (more CPU/RAM).

### 477. Horizontal vs vertical?
Vertical: simple, has a ceiling and single point of failure. Horizontal: near-unlimited and resilient but needs stateless design and distributed concerns.

### 478. Load balancing?
Distributes requests across instances using round-robin, least-connections, or IP-hash, with health checks removing bad nodes (Nginx, Azure LB, AWS ALB).

### 479. Stateless architecture?
Server keeps no per-user state in memory between requests; state lives in the DB/cache/token.

### 480. Why easier to scale?
Any instance can serve any request, so you can add/remove instances freely and recover from failures without losing sessions.

### 481. Reverse proxy?
A server in front of your app (Nginx, YARP, IIS) handling TLS, load balancing, caching, compression, and hiding the internal servers.

### 482. CDN?
Content Delivery Network: a global network of edge servers caching content close to users.

### 483. How can a CDN improve API performance?
Cache public GET responses at the edge (lower latency, less origin load), absorb traffic spikes, DDoS protection, TLS termination.

### 484. Asynchronous I/O?
Using OS-level non-blocking operations so no thread waits for disk/network.

### 485. Why does async I/O improve scalability?
Few threads can serve thousands of concurrent requests, since waiting requests hold no thread.

## 24. Distributed Systems & Microservices

### 486. Monolith?
One deployable application containing all features (UI, business, data) in a single codebase and process.

### 487. Microservice?
A small, independent service owning one business capability and its own database, deployed separately (Orders, Payments, Users services).

### 488. Monolith vs microservices?
| | Monolith | Microservices |
|---|---|---|
| Deploy | all together | independently |
| Scale | whole app | per service |
| Complexity | low | high |
| Team size | small | many teams |
| Failures | one bug can crash all | isolated |
Start with a well-structured (modular) monolith; split when needed.

### 489. Disadvantages of microservices?
Network latency and failures, distributed transactions, harder debugging/tracing, more DevOps work, data consistency issues, versioning of contracts, higher infrastructure cost.

### 490. Service-to-service communication?
How services talk: synchronous (HTTP/REST, gRPC) or asynchronous (messages/events via a broker).

### 491. REST vs gRPC?
REST: JSON over HTTP/1.1, human readable, browser friendly. gRPC: binary Protocol Buffers over HTTP/2, faster, strongly typed contracts (`.proto`), streaming.

### 492. When choose gRPC?
Internal service-to-service calls needing low latency/high throughput, streaming, polyglot teams with strict contracts. Use REST for public APIs.

### 493. Message-based communication?
Services send messages to a broker instead of calling each other directly; the receiver processes later (decoupled, resilient).

### 494. Message broker?
Middleware that routes/stores messages (RabbitMQ, Kafka, Azure Service Bus, AWS SQS).

### 495. RabbitMQ vs Kafka?
RabbitMQ: smart broker, queues, flexible routing, messages deleted after consumption; great for task queues. Kafka: distributed log, retains events, huge throughput, replayable, ordered partitions; great for event streaming/analytics.

### 496. Event-driven architecture?
Services publish events ("OrderPlaced") and others react to them without knowing each other.
```csharp
await _bus.Publish(new OrderPlaced(order.Id, order.Total));   // MassTransit
public class EmailConsumer : IConsumer<OrderPlaced> { public Task Consume(ConsumeContext<OrderPlaced> c) => ...; }
```

### 497. Eventual consistency?
Data across services may be temporarily different but becomes consistent after events propagate. (Your bank app shows the new balance a few seconds later.)

### 498. Distributed transaction?
A transaction spanning multiple databases/services needing all-or-nothing results.

### 499. Why difficult?
Network failures, partial success, no shared lock/rollback (2PC is slow and blocks), services may be down. Replaced by Saga/Outbox + eventual consistency.

### 500. Saga pattern?
A sequence of local transactions; if one fails, run **compensating** actions to undo the earlier ones.
```
Order Created → Payment Charged → Stock Reserved → Shipping Created
If stock fails → Refund Payment → Cancel Order
```
Choreography: services react to events. Orchestration: a central coordinator (MassTransit state machine) directs steps.

### 501. Outbox pattern?
Save the business data **and** the outgoing event in the same DB transaction (Outbox table). A background publisher later sends it to the broker and marks it sent. Avoids "DB saved but message lost".
```csharp
db.Orders.Add(order);
db.OutboxMessages.Add(new OutboxMessage("OrderPlaced", JsonSerializer.Serialize(evt)));
await db.SaveChangesAsync();   // atomic
```
Consumers must be idempotent (at-least-once delivery).

### 502. CQRS?
Command Query Responsibility Segregation: separate models for writes (commands) and reads (queries), often with MediatR.
```csharp
public record CreateStudentCommand(string Name) : IRequest<int>;
public record GetStudentQuery(int Id) : IRequest<StudentDto>;
```

### 503. CQRS pros and cons?
Pros: independent scaling/optimization of reads and writes, clear code, simpler queries. Cons: more code and complexity, eventual consistency if read DB is separate. Not for simple CRUD.

### 504. Event sourcing?
Store every change as an immutable event (`AccountCreated`, `MoneyDeposited`) instead of only the current state; rebuild state by replaying. Gives full audit and time travel; adds complexity.

### 505. Service discovery?
Finding service addresses dynamically (instances change): Consul, Kubernetes DNS, Eureka, cloud service registries.

### 506. API Gateway?
A single entry point for clients that routes to internal services (YARP, Ocelot, Azure APIM, Kong).

### 507. What problems does it solve?
Routing, authentication, rate limiting, aggregation of calls, SSL termination, caching, logging, versioning, hides internal topology.

### 508. Circuit breaker?
Stops calling a failing service for a period after repeated failures ("open"), then tries again ("half-open"), preventing cascading failures.

### 509. Retry pattern?
Automatically retrying transient failures (timeouts, 503).

### 510. Why can retries make a system worse?
Retry storms multiply load on an already struggling service, duplicates non-idempotent operations, and delay failure detection. Use backoff + jitter, limits, circuit breakers, idempotency.

### 511. Exponential backoff?
Wait longer after each failure: 1s, 2s, 4s, 8s (+ random jitter).

### 512. Timeout pattern?
Set maximum wait time for calls so threads/resources aren't tied up forever.

### 513. Bulkhead pattern?
Isolate resources (thread/connection pools) per dependency so one slow dependency can't consume everything (like ship compartments).

### 514. Resilience?
Ability to keep working and recover when parts fail (retry, timeout, breaker, fallback, bulkhead, redundancy).

### 515. Polly?
.NET resilience library (now `Microsoft.Extensions.Http.Resilience`).
```csharp
builder.Services.AddHttpClient("payments")
  .AddStandardResilienceHandler();    // retry + circuit breaker + timeout + bulkhead

// Manual Polly
var policy = Policy.Handle<HttpRequestException>()
    .WaitAndRetryAsync(3, n => TimeSpan.FromSeconds(Math.Pow(2, n)));
await policy.ExecuteAsync(() => client.GetAsync(url));
```

## 25. Advanced C# / .NET

### 516. Garbage collection?
Automatic memory management: the GC finds objects no longer reachable and frees their memory.

### 517. GC generations?
Objects are grouped by age so the GC can collect young (short-lived) objects often and old ones rarely.

### 518. Gen 0, 1, 2?
Gen 0: newly created, collected most often. Gen 1: survivors, a buffer. Gen 2: long-lived objects (and LOH), collected rarely (expensive).

### 519. Large Object Heap?
Special area for objects ≥ 85,000 bytes (big arrays/strings). Collected with Gen 2, not compacted by default → fragmentation. Avoid frequent large allocations; use `ArrayPool<T>`.

### 520. Causes of memory leaks?
Static references/collections that only grow, un-unsubscribed events, undisposed `IDisposable`s, captured closures, caches without limits, `HttpClient` misuse, singletons holding scoped data, timers.

### 521. Diagnose leaks?
`dotnet-counters` (watch GC heap), `dotnet-dump`/`dotnet-gcdump`, Visual Studio/JetBrains dotMemory, compare heap snapshots to find growing types and their roots.

### 522. IDisposable?
Interface with `Dispose()` for releasing unmanaged resources (files, connections, sockets).

### 523. using statement?
Automatically calls `Dispose()` at scope end, even on exception.
```csharp
using var conn = new SqlConnection(cs);   // disposed at end of method
```

### 524. IAsyncDisposable?
Async version (`DisposeAsync`) for resources that need async cleanup: `await using var tx = await db.Database.BeginTransactionAsync();`

### 525. Dispose() vs finalizer?
`Dispose()`: deterministic, called by you. Finalizer (`~Class`): called by GC at an unknown time, slower, last resort. Pattern: `Dispose` calls `GC.SuppressFinalize(this)`.

### 526. Dependency disposal?
The DI container disposes services it **created** (scoped at request end, singletons at shutdown). Don't dispose instances you didn't create, and don't `using` an injected service.

### 527. Delegate?
A type-safe reference to a method. `delegate int Calc(int a, int b); Calc add = (a,b) => a+b;`

### 528. Event?
A notification mechanism built on delegates: publisher raises, subscribers handle.
```csharp
public event EventHandler<OrderEventArgs>? OrderPlaced;
OrderPlaced?.Invoke(this, new OrderEventArgs(id));
```

### 529. Delegate vs event?
A delegate field can be invoked/replaced by anyone with access; an event only allows `+=`/`-=` outside, and only the owning class can raise it (safer encapsulation).

### 530. Func, Action, Predicate?
- `Func<T,TResult>`: returns a value. `Func<int,int,int> add`.
- `Action<T>`: returns void. `Action<string> log`.
- `Predicate<T>`: returns bool. `Predicate<int> isEven`.

### 531. Expression trees?
Code represented as data (a tree) that can be inspected/translated. EF Core turns `Expression<Func<Student,bool>>` into SQL.

### 532. Generics?
Type parameters so code works with any type safely: `List<T>`, `Result<T>`.

### 533. Why useful?
Type safety, reuse, no boxing, better performance.

### 534. Generic class vs generic method?
```csharp
public class Repository<T> where T : class { }            // class level
public static T Max<T>(T a, T b) where T : IComparable<T>  // method level
    => a.CompareTo(b) > 0 ? a : b;
```

### 535. Covariance and contravariance?
Covariance (`out`): use a more derived type where base is expected (`IEnumerable<Dog>` → `IEnumerable<Animal>`). Contravariance (`in`): use a more general handler where specific is expected (`Action<Animal>` → `Action<Dog>`).

### 536. Reflection?
Inspecting/creating types and members at runtime (`typeof(T).GetProperties()`). Used by DI, serializers, ORMs. Slower; prefer source generators when possible.

### 537. Attributes?
Metadata attached to code: `[Required]`, `[HttpGet]`, custom ones read via reflection.

### 538. Source generators?
Compiler plug-ins that generate code at build time (no runtime reflection): `System.Text.Json` source gen, Mapperly, `LoggerMessage`. Faster and AOT friendly.

### 539. Span<T>?
A stack-only, allocation-free view over contiguous memory (array, string slice, stack memory).
```csharp
ReadOnlySpan<char> part = "2025-01-15".AsSpan(0, 4);   // "2025" without allocating a new string
```

### 540. Memory<T>?
Like Span but can live on the heap, so it can be used in async methods and stored in fields.

### 541. When use Span<T>?
Hot paths: parsing, slicing strings/arrays, buffer handling, avoiding allocations. Don't bother in normal CRUD code.

### 542. Boxing performance overhead?
Heap allocation + copy + GC pressure + type check on unboxing. Avoid with generics and avoiding `object` params.

### 543. JIT compilation?
Just-In-Time: IL code is compiled to machine code when a method is first called (tiered compilation optimizes hot methods later). Slower startup, highly optimized at runtime.

### 544. AOT compilation?
Ahead-Of-Time: compile to native code at build time (`PublishAot`). Fast startup, small memory, no JIT; limits (reflection, dynamic loading).

### 545. JIT vs Native AOT?
JIT: max compatibility, dynamic features, slower startup. Native AOT: instant startup, lower memory, great for serverless/containers/microservices, but restricted features and larger build effort.

Rules: never store card data (use gateway tokens, PCI compliance), idempotency keys, statuses (`Initiated, Succeeded, Failed, Refunded`), webhook signature validation, retries with backoff, reconcile with gateway daily, full audit log, `decimal` + currency code.

### 554. File-upload API
```csharp
[HttpPost("upload"), RequestSizeLimit(50_000_000)]
public async Task<IActionResult> Upload(IFormFile file) {
    var allowed = new[] { ".jpg", ".png", ".pdf" };
    var ext = Path.GetExtension(file.FileName).ToLowerInvariant();
    if (!allowed.Contains(ext) || file.Length == 0) return BadRequest("Invalid file");
    var safeName = $"{Guid.NewGuid()}{ext}";                 // never trust client file name
    await using var fs = System.IO.File.Create(Path.Combine(uploadPath, safeName));
    await file.CopyToAsync(fs);
    return Ok(new { file = safeName });
}
```
Security: check size, extension **and** content signature, virus scan, store outside web root or in blob storage, no execution permission.

### 555. Upload a 1 GB file without exhausting memory?
- **Stream** instead of buffering (don't use `IFormFile` for huge files; read `Request.Body` or `MultipartReader`).
- **Chunked/resumable upload** (client sends 5-10 MB parts; tus protocol / S3 multipart).
- **Direct-to-storage** with a pre-signed URL (SAS token on Azure Blob) so the file never touches your API.
- Raise Kestrel `MaxRequestBodySize` for that endpoint only; disable form buffering.
```csharp
[HttpPost("stream"), DisableRequestSizeLimit]
public async Task<IActionResult> Stream() {
    await using var fs = System.IO.File.Create(path);
    await Request.Body.CopyToAsync(fs, HttpContext.RequestAborted);  // constant memory
    return Ok();
}
```

### 556. Pagination for 10 million records?
Use **keyset (cursor) pagination** on an indexed column: `WHERE Id > @lastId ORDER BY Id LIMIT 20`. Avoid `OFFSET` big values (scans skipped rows) and avoid `COUNT(*)` on every call (cache or approximate). Add covering indexes, project to DTO, cap page size, use `AsNoTracking`.

### 557. API takes 5 seconds, how to troubleshoot?
1. Reproduce and measure (timings per layer: network, middleware, DB, external calls). 2. Check APM/traces for the slowest span. 3. Check SQL (N+1, missing index, huge result). 4. Check external calls (timeouts). 5. Check sync-over-async/thread starvation (`dotnet-counters`). 6. Check payload size and serialization. 7. Fix biggest bottleneck, add caching, re-measure.

### 558. DB query takes 4 seconds, how to optimize?
Get the execution plan, look for table scans/key lookups, add index on WHERE/JOIN/ORDER BY columns (composite in right order, `INCLUDE` columns), select needed columns only, remove functions on indexed columns, paginate, update statistics, rewrite subqueries/joins, archive old data, consider caching/materialized views.

### 559. 10,000 requests per second, how to scale?
Stateless API → many instances behind a load balancer + autoscaling; async code; Redis cache + CDN for reads; DB read replicas, indexing, connection pooling, sharding if needed; queue slow writes; rate limiting; compression; load test (k6) and monitor p99.

### 560. Two users update the same record simultaneously
Optimistic concurrency with `RowVersion`/ETag:
```csharp
try { await db.SaveChangesAsync(); }
catch (DbUpdateConcurrencyException) {
    return Conflict("Record was changed by someone else. Reload and retry.");
}
```
For counters use atomic SQL (`SET qty = qty - 1`). Pessimistic lock only when conflicts are frequent.

### 561. Client sends the same payment five times
Require `Idempotency-Key`; store `(key, requestHash, response)` with a **unique index**. First request processes; duplicates return the saved response (or 409 if still in progress). Also pass the key to the payment gateway, and ensure the UI disables the button.
```csharp
try { db.IdempotencyKeys.Add(new(key)); await db.SaveChangesAsync(); }   // unique constraint
catch (DbUpdateException) { return await ReturnStoredResponse(key); }
```

### 562. API returns 500 errors randomly, investigate
Check logs with correlation IDs and stack traces, group errors by type/endpoint/time, check recent deployments, DB timeouts/pool exhaustion, memory/CPU, thread starvation, downstream failures, race conditions (shared state in singletons, DbContext misuse), specific instance (bad node), config differences. Add alerts, reproduce, fix, add tests.

### 563. Works locally but fails after deployment
Check: environment variables/config values, connection strings, DB firewall/network access, missing migrations, HTTPS/certificates, file paths and permissions, case-sensitive paths (Linux), runtime/SDK version, reverse proxy headers (`UseForwardedHeaders`), CORS, JWT keys/issuer differences, missing secrets, logs (`ASPNETCORE_ENVIRONMENT=Development` temporarily).

### 564. POST works locally but fails in production
Check request size limit (proxy `client_max_body_size`), CORS preflight, antiforgery/CSRF, redirect from HTTP to HTTPS turning POST into GET (301/302), WAF blocking, content-type/serialization differences, DB write permissions, validation differences, auth tokens, proxy/body stripped, timeouts.

### 565. GET works but POST/PUT/DELETE fail in production
Classic causes: server/proxy blocks verbs (IIS **WebDAV module** blocks PUT/DELETE), CORS preflight (`OPTIONS`) not allowed, WAF/firewall rules, read-only DB user, missing antiforgery/auth, HTTP→HTTPS redirect, load balancer config. Fix: remove WebDAV, allow verbs and OPTIONS, correct CORS, grant DB write rights.

### 566. Cannot connect to MongoDB/SQL Server in production
1. Read the exact exception (timeout, login failed, untrusted cert). 2. Verify connection string (host, port, credentials, `TrustServerCertificate`, TLS). 3. Network: DNS, firewall/security group, VNet, IP allow-list. 4. Test from the server with `telnet host 1433`/`mongosh`/`sqlcmd`. 5. Verify DB user permissions and that the server is running. 6. Check pool exhaustion and connection limits. 7. Confirm secrets/env vars loaded.

### 567. JWT works locally but fails after deployment
Check: signing key identical across instances (not a random key per instance), issuer/audience match the production values, token expiry/**clock skew** (server time sync), HTTPS/proxy stripping the `Authorization` header, middleware order (`UseAuthentication` before `UseAuthorization`), env vars missing, key too short, load balancer sending to instances with different configs, `WWW-Authenticate` response message for the exact reason.

### 568. CORS works locally but fails in production
Production frontend origin not in `WithOrigins` (scheme/host/port must match exactly, no trailing slash), `UseCors` placed wrong, credentials with wildcard origin, preflight `OPTIONS` blocked by proxy/WAF, headers/methods not allowed, CORS configured both in proxy and app (duplicate headers), error responses missing CORS headers. Debug in browser DevTools Network → check `Access-Control-Allow-*` headers.

### 569. API returns sensitive fields to clients
Immediately stop leak (hotfix), introduce response DTOs/projections, remove entity returns, add `[JsonIgnore]` as safety net, add tests that scan responses, rotate exposed secrets/force password resets, review logs/audits, code-review rule: never return entities.

### 570. Duplicate database queries
Enable EF logging (`LogTo(Console.WriteLine)`), use MiniProfiler/Application Insights to count queries per request, look for loops with queries (N+1), repeated service calls for the same data, lazy loading. Fix: `Include`/projection, load once and pass data, per-request caching, `Find` (checks tracker), batch IDs with `Contains`.

### 571. Endpoint vulnerable to SQL injection
Replace string concatenation with parameters/EF LINQ/`FromSqlInterpolated`, whitelist dynamic column/order-by names, validate input, least-privilege DB account, remove detailed errors, add WAF rules, test (sqlmap), rotate credentials if data may have leaked.

### 572. Memory continuously increases
Confirm it's a leak (not just GC lazy), track with `dotnet-counters`, take dumps/gcdump at intervals, compare heaps to see growing types, find roots (static lists, unbounded caches, event handlers, undisposed objects, `HttpClient` per request, large LOH allocations). Fix, add cache size limits and expiration, set container memory limits and alerts.

### 573. Occasionally times out under heavy traffic
Investigate thread-pool starvation (sync over async), DB connection pool exhaustion, slow queries/locks/deadlocks, downstream service latency, GC pauses, CPU saturation, rate limits, load balancer timeouts, cold instances. Add timeouts, bulkheads, circuit breakers, caching, autoscaling, and load test to reproduce.

### 574. Third-party payment API is unavailable
Fail gracefully: retry with exponential backoff for transient errors, circuit breaker to stop hammering, timeouts, mark payment `Pending` and queue it for later processing (don't charge twice, use idempotency), return `503` with `Retry-After` or `202 Accepted`, optional fallback gateway, alerts, tell the user clearly.

### 575. External service takes 30 seconds, avoid blocking
Set a short timeout (e.g., 3-5 s) with `CancellationToken`, run it as a background job (return `202 Accepted` + status URL), use a queue/worker and webhook/polling for the result, add circuit breaker and bulkhead, cache previous results, and always use async I/O.
```csharp
builder.Services.AddHttpClient("slow").AddStandardResilienceHandler(o => o.AttemptTimeout.Timeout = TimeSpan.FromSeconds(5));
```

# 🔴 27. Senior-Level System Design Questions

> Pattern for answering any design question: **Requirements → API → Data model → High-level architecture → Scaling → Failure handling → Security → Monitoring.**

### 576. Scalable REST API architecture for 10 million users
```
Client → CDN → WAF → Load Balancer → API instances (stateless, autoscaled)
                                         ├→ Redis (cache, rate limit)
                                         ├→ SQL primary → read replicas
                                         └→ Message broker → background workers
```
Stateless .NET API in containers (Kubernetes), JWT auth, cache-aside, read replicas, async via queues, cursor pagination, rate limiting, observability (OpenTelemetry), CI/CD, autoscaling on CPU/RPS. Shard the DB by tenant/user id when one primary is not enough.

### 577. Highly available .NET backend
No single point of failure: ≥ 2-3 instances across availability zones, load balancer with health checks, DB with automatic failover (Always On / managed HA), Redis with replicas, retries + circuit breakers, graceful shutdown, zero-downtime deploys, backups and tested disaster recovery (RPO/RTO), multi-region if required.

### 578. Distributed authentication system
Central **Identity Provider** (OpenIddict/Keycloak/Entra) issues JWTs signed with asymmetric keys (RS256). Services validate tokens locally using the public JWKS endpoint (no call per request). Refresh tokens stored in DB/Redis with rotation, SSO with OIDC, API gateway enforces auth, client-credentials for service-to-service, key rotation with `kid`, MFA, audit logs.

### 579. Scalable notification service
```
Producers → Queue/Topic (Kafka/Service Bus) → Notification workers
                                  ├→ Email (SendGrid)  ├→ SMS  └→ Push (FCM/APNs)
```
Components: templates, user preferences, per-channel queues, retries with backoff and dead-letter queue, idempotency (no duplicate notifications), rate limits per provider, delivery status tracking, batching. API: `POST /notifications` returns 202.

### 580. API rate-limiting system
Algorithms: fixed window, sliding window, **token bucket** (allows bursts), leaky bucket. Store counters in **Redis** (atomic `INCR` + `EXPIRE` or Lua script) so all instances share limits. Key by API key/user/IP. Return `429 Too Many Requests` + `Retry-After`, `X-RateLimit-*` headers. Enforce at gateway plus per-endpoint limits; different tiers per plan.

### 581. Distributed caching architecture
Layered: browser/CDN → local in-memory (L1) → Redis cluster (L2) → DB. Cache-aside with TTL + jitter, invalidate on write (or publish invalidation events), consistent hashing/Redis Cluster for sharding, replicas for HA, stampede protection (locks/`HybridCache`), eviction policy (LRU), monitor hit ratio.

### 582. Order-processing system using .NET and messaging
```
API → Orders DB + Outbox → Broker
Broker → Payment Service → PaymentCompleted
       → Inventory Service → StockReserved
       → Shipping Service
Saga orchestrator (MassTransit) coordinates, compensates on failure
```
Use idempotent consumers, Outbox pattern, retries + dead-letter queues, order state machine, correlation IDs for tracing, eventual consistency, status endpoint for clients.

### 583. Payment processing system with idempotency
Client sends `Idempotency-Key` → API stores key + request hash (unique index) → creates `Payment(Pending)` → calls gateway with the same key → updates status → saves response for replay. Use webhooks to confirm final status, reconcile daily, outbox for events, never store raw card data, encrypt sensitive data, full audit trail, retry with backoff.

### 584. File-processing service using background workers
Upload goes directly to blob storage (pre-signed URL) → storage event/API enqueues a job message → worker pool (BackgroundService/Hangfire/Azure Functions) processes (virus scan, resize, parse) → writes result + updates job status (`Queued → Processing → Done/Failed`) → client polls `/jobs/{id}` or gets a webhook. Autoscale workers by queue length, DLQ for poison messages, idempotent processing.

### 585. URL-shortening service
- **API:** `POST /shorten {url}` → `{ shortCode }`; `GET /{code}` → `301/302` redirect.
- **ID generation:** auto-increment/distributed ID (Snowflake) → **Base62** encode (7 chars ≈ 3.5 trillion).
- **Storage:** key-value DB (`code → longUrl`), read-heavy.
- **Scale:** Redis cache for hot codes, CDN, replicas, analytics via async events, expiry/TTL, abuse/spam detection, rate limiting.
```csharp
static string ToBase62(long n) { const string c = "0-9a-zA-Z"; /* divide by 62 loop */ }
```

### 586. API Gateway architecture
Gateway (YARP/Ocelot/Kong/APIM) in front of services: routing, TLS termination, authentication/JWT validation, rate limiting, request aggregation (BFF), caching, versioning, logging/tracing, circuit breaker. Run it highly available (multiple instances) and keep business logic out of it.

### 587. Microservices architecture for e-commerce
Services: Identity, Catalog, Cart, Orders, Payments, Inventory, Shipping, Notifications, Search. Each owns its DB (database per service). Sync calls via gateway/gRPC for queries; async events (Kafka/RabbitMQ) for workflows; Saga for checkout; Outbox; Redis for cart/catalog cache; Elasticsearch for search; CDN for images; Kubernetes; centralized logs/tracing; CI/CD per service.

### 588. Logging and monitoring architecture
Apps (Serilog + OpenTelemetry) → collector/agents → pipeline (Kafka/Fluentd) → storage (Elasticsearch/Loki, Prometheus for metrics, Jaeger/Tempo for traces) → dashboards (Grafana/Kibana) + alerting (PagerDuty). Include correlation IDs, structured logs, the RED metrics (Rate, Errors, Duration), health checks, SLOs, retention/PII masking.

### 589. Audit logging system
Capture **who, what, when, where, old value, new value** for every important action. Source: EF `SaveChangesInterceptor` or domain events → append-only `AuditLog` (never updated/deleted; write-once storage) → publish through a queue to avoid slowing requests. Index by entity/user/time, retention policy, tamper-evidence (hash chain), restricted read access, searchable UI.

### 590. Distributed job-processing system
Job API → durable queue (partitioned) → worker fleet (competing consumers) → results store. Features: scheduling (cron), priorities, retries with backoff, DLQ, idempotent jobs, **distributed locks/leader election** (Redis/ZooKeeper) so a job runs once, heartbeat/visibility timeout for crashed workers, autoscaling, job status tracking, observability. (Hangfire, Quartz.NET, Temporal.)

### 591. Real-time notification system
Clients connect via **WebSockets/SignalR** (fallback SSE/long-poll). Multiple servers need a backplane (Redis pub/sub / Azure SignalR) so a message reaches the right connection. Flow: event → broker → notification service → push via SignalR to online users, queue/mobile push for offline users, store unread in DB, ack/read receipts, authentication on connect, scale connections horizontally with sticky or managed service.
```csharp
await _hub.Clients.User(userId).SendAsync("notify", payload);
```

### 592. API that survives database failure
Primary DB with automatic failover + replicas; serve reads from replicas/cache when primary is down (graceful degradation); queue writes (Outbox/queue) and replay later; circuit breaker + timeouts; retries with backoff (`EnableRetryOnFailure`); return `503` for non-critical paths; multi-AZ/region, backups + tested restore; health checks removing unhealthy nodes.

### 593. API with zero-downtime deployment
Multiple instances behind a load balancer. **Rolling update / Blue-Green / Canary:** start new version → readiness check passes → shift traffic gradually → drain old instances (graceful shutdown) → rollback if errors rise. DB changes use **expand/contract** (backward-compatible migrations: add column → deploy code → backfill → remove old later). Use feature flags, health probes, and automated pipelines.

### 594. Multi-tenant SaaS backend
Tenant models: **shared DB + `TenantId` column** (cheapest), **schema per tenant**, **DB per tenant** (best isolation). Resolve tenant from subdomain/header/JWT claim in middleware, store in a scoped `ITenantContext`, apply EF **global query filter** `e.TenantId == _tenant.Id`, set tenant automatically on save, per-tenant config/limits/rate limits, tenant-aware caching keys, encryption, backups, onboarding automation, noisy-neighbor protection.
```csharp
modelBuilder.Entity<Order>().HasQueryFilter(o => o.TenantId == _tenant.Id);
```

### 595. Backend that supports horizontal scaling
Keep servers **stateless** (no in-memory sessions; use JWT/Redis), externalize state (DB, cache, blob storage, queue), share data-protection keys and config, use a load balancer with health checks, idempotent operations, distributed locks where needed, centralized logging, autoscaling rules, DB scaling (replicas/sharding), async messaging for heavy work, containers/Kubernetes.
